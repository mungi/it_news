## Deep Dive

### F5 BIG-IP APM `CVE-2026-94127`: OAuth authorization server data-plane RCE를 identity control-plane incident로 닫는 방법

한 줄 결론: active exploitation이 공지된 `CVE-2026-94127`은 management interface가 아니라 OAuth authorization server virtual server로 들어오는 인증 전 RCE 범위임. affected profile·access policy·virtual server를 구성으로 식별하고, hotfix 또는 support iRule, OAuth/host forensic, HA 검증, credential·token review를 하나의 closure로 운영 필요.

- 일일 재검토: 2026-09-24 02:05 KST

#### 한 줄 결론

`CVE-2026-94127`은 BIG-IP APM OAuth authorization server virtual server의 heap-based buffer overflow이며 F5가 active exploitation을 공지한 결함임. management VLAN ACL 점검만으로 끝내지 말고 external OAuth traffic path, affected binding, host-level evidence, issued-token 영향 범위를 같은 incident record로 묶어야 함.

- 우선순위: CVSS v3.1 `9.8`, CISA KEV 등록, internet-facing token endpoint 가능성
- 완료 기준: affected virtual server의 fixed-or-mitigated 상태와 OAuth·HA·forensic evidence 동시 확인

#### 원문과 관련 뉴스의 핵심 내용

F5는 APM이 OAuth authorization server로 access token을 발급하고 access policy와 OAuth authorization server profile이 같은 virtual server에 연결된 경우를 영향 조건으로 설명함. 공개 보도 기준 affected train은 hotfix 이전 `21.1.0`, `17.5.0`~`17.5.1`, `17.1.0`~`17.1.3`이며 End of Technical Support release는 안전하다고 해석할 근거가 없음.

- 범위: OAuth client 또는 resource server 역할만 수행하고 authorization server profile이 없는 구성은 F5 정정 기준 비영향
- 경계: 공격자·피해 조직·침해 규모·hotfix 이후 attacker access 제거 여부는 공개 source 미확인

#### AI/Infra 전문가 해석

이 결함의 asset 단위는 BIG-IP appliance 한 대가 아니라 token issuer 역할을 하는 virtual server 조합임. CMDB version, LTM virtual server, APM access policy, OAuth profile, public DNS·WAF·load balancer path를 조인하지 않으면 실제 exposed endpoint를 놓치거나 비영향 구성까지 불필요하게 중단할 수 있음.

- 볼 것: token endpoint·authorization endpoint·redirect URI·OAuth client와 virtual server binding의 configuration export
- 피할 것: management interface가 private network라는 사실을 data-plane OAuth RCE의 차단 증거로 사용하는 판단

#### 아키텍처·운영 관점

authorization server compromise 가정에서는 token 발급뿐 아니라 OAuth client configuration, redirect URI, access policy, administrator command와 traffic policy integrity를 조사 범위에 넣어야 함. HA pair에서는 active 장비만 고치고 peer에 mitigation 또는 hotfix가 빠지는 상태가 failover 시 재노출과 configuration drift로 이어질 수 있음.

- 검증: active/standby release·iRule·sync 상태와 OAuth login, token issuance, callback negative test 확인
- 기록: asset owner·IdP owner·application owner·network owner별 change approval과 rollback owner 지정

#### 보안·forensic 관점

F5가 제시한 신호는 `/var/log/apm`의 반복 failed UserInfo request, `tmctl global_oauth_stat -s total_requests,total_userinfo_requests,total_failed`의 설명되지 않는 `total_failed` 증가, `/var/log/audit` suspicious command, TMM SIGABRT/core의 시간 상관임. 신호 하나만으로 침해를 확정하지 않고 patch 전후 동일 시간창에서 configuration·host·OAuth telemetry를 보존해야 함.

- hunt: virtual server access, APM/audit log, TMM core, administrator change, OAuth client·redirect URI 변경 대조
- 보존: hotfix/iRule 이전 log·core·UCS/configuration export와 time synchronization evidence 확보

#### 비용·가용성 관점

emergency hotfix는 authentication path의 availability와 변경 리스크를 동시에 만듦. planned maintenance와 별개로 canary client, success/failure ratio, p95 authorization latency, callback error, token issuance, HA failover를 release gate로 측정해야 하며, iRule은 final hotfix를 대체하는 장기 예외가 아님.

- 측정: fixed-or-mitigated virtual server 비율, failed OAuth 비율, TMM crash, rollback time
- 운영 과제: support-issued iRule의 scope·expiry·peer parity와 final hotfix window 추적

#### 도입·대응 로드맵

첫 단계는 configuration-led inventory로 affected role을 판정하는 것임. 다음으로 vendor hotfix 또는 support-issued iRule을 HA pair에 일관되게 적용하고, OAuth transaction canary와 host/identity hunt를 병렬 수행함. 마지막으로 token·session·administrator credential 회전 범위를 local evidence와 application dependency에 따라 결정해야 함.

- 1단계: version·authorization-server profile·access policy·virtual server exposure inventory
- 2단계: hotfix/iRule 적용 뒤 OAuth success·failure·HA·application synthetic 검증
- 3단계: forensic 결과로 token/session/client secret/administrator credential review와 recovery scope 결정

#### 개발팀/인프라팀 체크리스트

네트워크팀·IAM팀·플랫폼팀·SOC의 증거가 분리되면 closure 품질이 낮아짐. configuration object와 traffic signal을 같은 change window로 정렬하고, application owner가 redirect와 callback regression을 확인해야 함.

- 네트워크팀: public path, virtual server, WAF/LB, HA peer와 iRule/hotfix 상태 확인
- IAM팀: OAuth issuer·client·redirect URI·token/session 정책 및 anomalous failure 검토
- SOC/플랫폼팀: APM/audit/TMM evidence 보존, suspicious command·crash·configuration change hunt

#### 강조 메세지

이번 대응의 판단 단위는 BIG-IP patch 여부가 아니라 OAuth authorization server data-plane이 실제로 fixed-or-mitigated인지와 identity control-plane integrity가 검증됐는지임. “management interface 비노출”과 “OAuth virtual server 비영향”을 혼동하지 않는 asset evidence가 필요함.

- 팀 액션: 24시간 내 affected binding inventory와 hotfix/iRule·HA parity·OAuth canary 결과를 한 장의 closure record로 제출
- 발표 메세지: active exploitation 대응은 patch 속도와 함께 token issuer traffic·host forensic·failover 증거를 요구함

### Amazon CloudWatch Omni GA: cross-account agent telemetry를 운영 control plane으로 도입하는 관측성 설계

한 줄 결론: CloudWatch Omni는 AWS account·Region·Azure workload telemetry와 agent prompt·model call·tool invocation evaluation을 central space에서 연결하는 GA 기능임. AI-assisted root-cause 기능을 자동 의사결정으로 쓰기보다 OTel completeness, data boundary, retention, human escalation, query cost를 canary와 SLO로 검증하는 control plane으로 도입 필요.

- 일일 재검토: 2026-09-24 02:05 KST

#### 한 줄 결론

CloudWatch Omni는 application telemetry와 agent evaluation을 계정·리전 경계를 넘어 한 central space에서 보는 CloudWatch 운영 경험임. 단일 화면은 observability access와 data retention을 자동으로 안전하게 만들지 않으므로, agent trace completeness·prompt redaction·human escalation·query cost를 release control로 명시해야 함.

- 변화: AWS account·Region·Azure workload와 agent signal을 central account space에서 조회
- 판정: AI-assisted diagnosis는 incident commander·SLO owner를 대체하지 않는 triage assist

#### 원문과 관련 뉴스의 핵심 내용

AWS는 CloudWatch Omni가 OpenTelemetry 상호운용성과 CloudWatch 운영 기능을 결합한다고 발표함. service·dependency 자동 발견, golden metric, natural-language chat, console guided path, AWS Agent Toolkit telemetry query와 AWS DevOps Agent root-cause 지원이 포함됨. GA 시작 리전은 US East (N. Virginia), US West (Oregon), Europe (Ireland)임.

- 범위: central account의 space에서 다수 AWS account·Region과 Azure telemetry 연결
- 경계: Seoul workload 제공 여부·cross-region data path·residency는 console, contract, organization policy로 별도 확인 필요

#### AI/Infra 전문가 해석

agent service는 HTTP error rate만으로 품질을 판단하기 어려움. prompt, model call, tool invocation, evaluation score, downstream latency, human correction을 trace context로 연결해야 재시도 증가와 tool permission failure, 모델 변경 영향, token 비용을 같은 release record에서 설명할 수 있음.

- 볼 것: deployment SHA·model version·prompt template·tool version·trace ID·evaluation dataset의 provenance 연결
- 피할 것: chat root-cause 답변을 source log·metric·trace 링크 없이 incident conclusion으로 승격하는 흐름

#### 아키텍처·telemetry 관점

OpenTelemetry 도입은 span을 보내는 단계가 아니라 resource attribute, trace propagation, sampling, log correlation, cardinality budget의 contract를 만드는 작업임. account·Region·Azure를 central space에 연결할 때 workload identity와 least-privilege read path, ownership label을 표준화하지 않으면 dashboard는 늘고 incident 책임은 흐려짐.

- 설계: service·environment·tenant sensitivity·model·tool·release를 bounded attribute taxonomy로 정의
- 검증: critical request의 end-to-end trace completeness와 cross-account access-denied signal을 canary 지표로 설정

#### 보안·거버넌스 관점

agent telemetry에는 prompt, tool input/output, user identifier, business data가 포함될 수 있음. central aggregation 전 source account의 data classification, redaction, encryption, retention, export 권한, break-glass query, audit logging을 정해야 하며 local IDE extension 사용과 production telemetry 권한은 분리해야 함.

- 통제: role별 query scope, sensitive attribute allowlist, redaction test, retention/ deletion owner 지정
- 리스크: debug 편의를 위한 full prompt/tool payload 수집이 cross-account data exposure와 비용 증가로 이어지는 경로

#### SRE·FinOps 관점

Omni의 service discovery와 AI-assisted analysis는 ingestion·storage·query·evaluation 비용 및 false-positive escalation을 수반함. 운영팀은 root-cause suggestion 채택률보다 MTTA/MTTR, trace coverage, query spend, evaluation latency, alert-to-human escalation precision을 baseline과 비교해야 함.

- 측정: OTel trace completeness, p95 query latency, diagnostic false-positive, human escalation time, telemetry cost per request
- 운영 과제: sampling·retention·cardinality threshold와 budget alert를 SLO review에 포함

#### 도입 로드맵

처음부터 모든 account와 agent framework를 연결하지 말고 customer-facing agent 한 개와 critical tool 한 개를 대상으로 시작함. 기존 APM/SIEM/runbook ownership을 유지한 채 OTel trace·evaluation·SLO·cost attribution을 연결하고, redaction과 access review를 통과한 뒤 account·Region·Azure 범위를 확대하는 순서가 안전함.

- 1단계: one service, one tool, one owner의 trace/evaluation/SLO canary
- 2단계: central query role·redaction·retention·cost budget과 incident handoff drill 검증
- 3단계: account/Region/Azure expansion 전 data residency와 access audit evidence review

#### 개발팀/인프라팀 체크리스트

개발팀은 agent evaluation을 production success의 유일한 proxy로 쓰지 않고 user outcome·fallback을 함께 기록해야 함. 플랫폼팀은 OTel contract와 IAM/retention을, SRE는 escalation과 budget을 소유해야 함.

- 개발팀: prompt/model/tool release와 evaluation dataset·trace context를 deployment record에 연결
- 플랫폼팀: cross-account role, attribute taxonomy, redaction, retention, IDE/local boundary 확인
- SRE/FinOps: SLO·runbook·human escalation·sampling·query spend와 budget alert 검증

#### 강조 메세지

CloudWatch Omni 도입의 산출물은 AI chat 화면이 아니라 agent와 application의 행동·품질·비용·책임자를 추적할 수 있는 evidence chain임. 통합 조회 권한을 넓히기 전에 최소 trace schema와 data boundary를 고정해야 운영 속도와 감사 가능성을 함께 확보할 수 있음.

- 팀 액션: 이번 주 agent 하나에 OTel span·tool evaluation·SLO·runbook·budget tag를 연결한 2주 canary 실행
- 발표 메세지: cross-account observability는 dashboard 프로젝트가 아니라 identity·data governance·SRE·FinOps 공동 control plane 과제

### 2. Linux AF_UNIX `CVE-2026-80521`: Ubuntu LTS 미패치 container escape·host-root exploit 공개 보도

- 발행: 2026-09-23 20:12 KST
- 분류: Security | 태그: Security, Linux, Ubuntu, Container, Kubernetes, AF_UNIX, CVE-2026-80521
- 출처: [The Hacker News / Debian Security Tracker](https://thehackernews.com/2026/09/exploit-released-for-unpatched-ubuntu.html)

핵심: Linux AF_UNIX garbage collector use-after-free `CVE-2026-80521`은 container에서 host root로 escape할 수 있는 경로로 보도됐고 Ubuntu 26.04 target exploit code가 공개됨. Ubuntu 26.04·24.04·22.04 LTS의 fix 배포 상태와 running kernel·container seccomp·untrusted workload를 즉시 대조 필요.

보도는 upstream fix가 8월 6일 반영됐으나 Ubuntu LTS에 fix가 배포되지 않았고, AF_UNIX socket은 Docker·Kubernetes seccomp profile에서 기본 허용된다고 설명함. CISA KEV 등재와 실제 exploitation은 source에서 확인되지 않아 active exploitation으로 단정하지 않음.

#### 무슨 일이 있었나

The Hacker News는 Linux kernel AF_UNIX socket subsystem use-after-free `CVE-2026-80521`이 container escape와 host root 경로가 될 수 있고 DepthFirst가 Ubuntu 26.04 target exploit code를 공개했다고 보도함.

- 공개: public exploit code는 Ubuntu 26.04 target 범위
- 경계: CISA KEV 등재와 실제 공격 사용은 source에서 확인되지 않음

#### 기술 원인

AF_UNIX garbage collector는 SCM_RIGHTS로 전달된 file descriptor를 정리함. socket edge가 GC에 공개된 뒤 skb queue 이전에 concurrent close와 GC가 일어나면 linked socket group 일부 해제와 stale pointer가 남을 수 있는 race가 CVE description에 설명됨.

- 원인: AF_UNIX SCC garbage collection의 edge publication·queue ordering race
- 영향 조건: local IPC와 affected kernel path·attacker controlled process의 결합

#### Ubuntu·container 운영 범위

보도는 upstream fix가 8월 6일 반영됐으나 Ubuntu 26.04·24.04·22.04 LTS에는 fix가 배포되지 않았다고 설명함. Docker·Kubernetes seccomp profile에서 AF_UNIX socket이 기본 허용된다는 점이 container reachability 조건임.

- inventory: distribution package status와 running kernel·reboot pending을 별도 확인

### 50. Kubernetes CSI Changed Block Tracking Beta: `v1beta1` CRD 전환과 snapshot metadata client migration

- 발행: 2026-09-15 03:30 KST
- 분류: Infra | 태그: Kubernetes, CSI, Storage, Backup, Snapshot, API, Open Source
- 출처: [Kubernetes Blog / SIG Storage](https://kubernetes.io/blog/2026/09/14/csi-changed-block-tracking-beta/)

- 공개: `external-snapshot-metadata` `v1.0.0`에서 CSI Changed Block Tracking(CBT)이 Beta로 승격
- 변경: `SnapshotMetadataService`가 `cbt.storage.k8s.io/v1alpha1`에서 **`v1beta1`**로 이동하고 구 API 병행 제공 없음
- 조건: Kubernetes `1.33+`, CSI spec `1.10+`, `csi-snapshot-metadata:v1.0.0` 조합 공개
- 범위: block volume snapshot metadata 대상이며 file volume·network file-share changed-list tracking은 제외
- 팀 액션: backup controller·manifest·CRD client를 자동 변환 없는 API migration으로 inventory하고 restore/metadata delta canary 필요

Kubernetes SIG Storage는 `external-snapshot-metadata` v1.0.0에서 CSI Changed Block Tracking(CBT)을 Beta로 올리고 `SnapshotMetadataService` CRD를 `cbt.storage.k8s.io/v1beta1`로 전환했다. schema는 바뀌지 않았지만 `v1alpha1`을 함께 제공하지 않아 Alpha 사용자는 CRD, manifest API version, CRD를 호출하는 client/controller 코드를 모두 바꿔야 한다. 기능은 block volume의 snapshot metadata와 allocated/delta metadata 조회를 대상으로 하며, file volume·network file-share의 changed-list tracking은 범위 밖이다. CSI driver support, Kubernetes·CSI spec·sidecar version, backup application의 delta metadata 처리와 restore drill을 같은 compatibility gate에서 검증해야 한다.

#### 무슨 일이 있었나

Kubernetes SIG Storage가 `external-snapshot-metadata` `v1.0.0`에서 CSI Changed Block Tracking(CBT)을 Alpha에서 Beta로 승격함. 변경의 중심은 `SnapshotMetadataService` CRD API version 전환임.

- 공개: `cbt.storage.k8s.io/v1alpha1` 대신 **`cbt.storage.k8s.io/v1beta1`** CRD 제공
- 범위: CSI snapshot metadata에서 allocated block과 changed block delta 조회를 지원하는 API

#### API migration 범위

schema 자체는 같지만 Beta release는 Alpha API를 함께 serving하지 않음. 기존 object와 control-plane integration은 version field만 바꾸는 무중단 전환으로 가정할 수 없음.

- 필수 변경: `v1.0.0` release의 CRD definition 재적용
- 필수 변경: `SnapshotMetadataService` manifest의 `apiVersion`과 CRD client/controller reference 수정
- 경계: `v1alpha1`에서 `v1beta1`으로 automatic conversion이 없다는 source 명시

#### 지원 조건과 기능 경계

원문은 minimum Kubernetes `1.33`, CSI spec `1.10+`, `registry.k8s.io/sig-storage/csi-snapshot-metadata:v1.0.0`을 compatibility 조건으로 제시함. 모든 volume type과 driver에 포괄 적용되는 기능은 아님.

- 전제: CSI driver가 volume snapshot과 `external-snapshot-metadata` sidecar를 지원하는 조합
- 제외: file volume과 network file-share changed-list tracking은 현재 기능 범위 밖

#### 시사점

CBT는 backup application의 incremental chain·snapshot orchestration과 연결될 수 있어 CRD apply 성공만으로 migration을 끝낼 수 없음. metadata delta의 정확성과 restore path를 함께 검증해야 함.

- 검증: `GetMetadataAllocated`·`GetMetadataDelta` client response와 snapshot/restore 결과를 pre/post migration 비교
- 운영: CSI driver·sidecar·Kubernetes version matrix, RBAC, GitOps rollback, retention chain을 하나의 change record로 관리
- 팀 액션: representative block-volume workload에서 full backup·incremental backup·restore와 controller rollback drill 수행

- 시사점: Alpha CBT 사용 조직은 `v1alpha1` CRD reference, GitOps manifest, controller RBAC/client, CSI driver/sidecar version을 inventory하고 `GetMetadataAllocated`·`GetMetadataDelta` 결과와 restore chain을 canary에서 비교 필요.
