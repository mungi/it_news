### Coldcard seed-generation 결함: hardware wallet patch가 아닌 key rotation incident로 대응

핵심: Coldcard의 2021년 firmware integration error가 deterministic PRNG를 seed generation에 연결했을 수 있다는 보도와 emergency firmware 배포는 이미 생성한 seed의 entropy를 복구하지 않음. 영향 가능 key는 firmware patch만으로 종료하지 말고 new seed, asset migration, multisig independence, on-chain reconciliation을 하나의 custody remediation으로 운영 필요.

- 일일 재검토: 2026-08-03 03:54 KST

#### 한 줄 결론

Coldcard seed-generation 결함 대응의 단위는 firmware patch가 아니라 **노출 가능 seed의 폐기·새 entropy 생성·자산 이전 증적**. 이미 생성된 secret은 업데이트로 entropy가 복구되지 않으므로 key lifecycle incident로 운영 필요.

- 결정: seed 생성 당시 firmware와 entropy ceremony를 exposure 판정의 기준으로 사용
- 팀 액션: custody migration을 key rotation·address ownership·transfer confirmation이 포함된 change record로 승인

#### 원문과 관련 뉴스의 핵심 내용

The Hacker News는 2026-08-02 Coldcard의 2021년 firmware integration error가 STM32 hardware RNG 대신 deterministic software PRNG를 seed generation에 연결했을 수 있다고 보도. Galaxy Research의 1,196개 주소·1,082.65 BTC·41분 sweep 분석과 Coinkite emergency firmware 배포도 함께 전함.

- 기술 조건: device UID·timer state·prior RNG-call history를 알거나 제약할 때 offline candidate stream 재현 가능성이라는 보도
- 대응 범위: Coinkite가 영향 model·release track용 emergency firmware를 배포했다는 보도
- 증거 경계: address sweep이 결함으로 인한 theft, 피해 seed 일치, 공격자 신원을 독립 증명하지 않음

#### 취약성 메커니즘과 증거 경계

기존 raw capture는 `MICROPY_HW_ENABLE_RNG` macro 존재만 확인한 조건 때문에 disabled configuration에서도 Yasmarang fallback이 binding된 것으로 Block 분석을 인용. fallback이 chip UID와 timer register로 초기화되고 fresh entropy를 수집하지 않았다는 설명 역시 해당 분석 범위임.

- 조건: firmware branch·device model·UID exposure·boot timing·prior RNG call이 attack cost를 바꾸는 변수
- 금지: 하나의 reported failure를 모든 Coldcard·hardware wallet·BIP-39 seed의 동일 위험으로 일반화하지 않기
- 확인: seed 생성 시점의 firmware window가 현재 installed version보다 우선하는 inventory key

#### AI/Infra 전문가 해석

entropy defect는 signing workload의 availability 문제가 아니라 trust anchor의 unpredictability를 훼손하는 failure. secure element·air gap·PIN·multisig는 서로 다른 control이지만, seed generation provenance가 약하면 downstream signing policy만으로 root secret의 searchability를 상쇄하지 못함.

- 해석: device firmware와 build configuration은 cryptographic key ceremony의 일부로 취급
- 해석: key material exposure는 CVE patch KPI가 아니라 rotated balance·retired address·recovery evidence로 측정
- 운영 과제: hardware wallet, HSM, KMS의 entropy source·firmware provenance·key-created-at inventory 연결

#### custody architecture 관점

seed는 device asset이 아니라 root-of-trust material. firmware defect는 signing policy와 별개로 key generation provenance를 훼손하며, multisig도 quorum signer가 같은 codebase·entropy defect에 집중되면 독립 control이 되지 않음.

- 설계: signer별 vendor·firmware·entropy source·seed ceremony·backup location을 quorum inventory로 관리
- 설계: new seed generation과 old address decommission을 separate approval·dual control·timed transfer로 분리
- 검증: derivation path·passphrase dependency·watch-only address·recovery procedure를 migration 전에 재현

#### security·incident response 관점

영향 가능 seed의 공개/비공개 노출 여부와 무관하게 대응은 predictable secret hypothesis로 시작해야 함. firmware patch만 적용하고 old seed를 restore하면 vulnerable secret을 계속 쓰는 경로가 될 수 있으므로 remediation completion 기준을 asset migration으로 정의 필요.

- contain: affected firmware/model/user cohort·balance·address activity를 제한된 incident record로 inventory
- eradicate: patched firmware에서 new seed를 만들고 old funds와 receiving address를 단계적으로 이동
- preserve: firmware version·device serial/UID handling policy·transaction ID·approval·customer notice를 감사 증적으로 보존

#### operations·FinOps 관점

custody migration은 on-chain fee·confirmation delay·market exposure·customer support·withdrawal limit을 함께 가진 change. 낮은 fee만 최적화하면 queue가 길어지고, 일괄 전송만 최적화하면 blast radius가 커질 수 있어 tranche와 reconciliation SLO가 필요.

- measure: migrated balance ratio·unmigrated high-risk balance·confirmation latency·failed transfer·support backlog
- plan: fee budget·daily transfer limit·multisig quorum availability·rollback 불가 transaction의 escalation owner 지정
- reconcile: source address·destination address·expected amount·fee·confirmation·ledger posting을 independent checker로 대조

#### 도입·복구 로드맵

1차 대응은 affected window 식별과 transfer freeze policy 수립. 이어 소액 canary로 new key generation·backup restore·signing·broadcast·reconciliation을 검증한 뒤 cohort별 migration을 실행하는 방식이 안전.

- 1단계: firmware/model/seed-created-at/entropy method/signing topology inventory
- 2단계: new seed·backup recovery·watch-only monitoring·small transfer canary 수행
- 3단계: tranche migration·on-chain confirmation·customer communication·old key retirement closure

- 분류: Microsoft가 AD CS improper authorization 결함으로 추적하는 `CVE-2026-54121`, 보도 인용 CVSS **8.8**
- 상태: Microsoft 7월 14일 업데이트가 배포됐고, 7월 24일 기준 보도에서 in-the-wild exploitation 보고는 확인 불가
- 변화: 공개 PoC가 일반 domain account에서 Domain Controller identity 획득까지의 재현 경로를 자동화

#### 공격 전제와 인증서 발급 경로

보도된 체인은 CA가 enrollment chase의 requester-supplied `cdc` host를 실제 Domain Controller인지 먼저 검증하지 않은 경로를 악용함. CA가 SMB·LDAP로 attacker-controlled listener에 연결한 뒤 Netlogon relay를 거치게 하는 구성임.

- 전제: network access와 domain account, Enterprise CA, default Machine template, CA에서 공격자 SMB 445·LDAP 389 listener까지의 reachability 필요
- 계정: 기본 `ms-DS-MachineAccountQuota` 값 **10**에서 computer account를 생성하거나 기존 제어 account를 재사용 가능한 조건
- 속성: 공격자가 DC의 `objectSid`·`dNSHostName`을 반환하고 CA가 target DC identity를 certificate에 서명하는 보도된 chain

#### 영향과 범위

발급된 PFX를 PKINIT에 사용하면 target Domain Controller로 Kerberos authentication을 수행하고 DCSync를 통해 `krbtgt`를 포함한 account secret 요청으로 이어질 수 있음. 이는 PoC와 보도에 근거한 영향 경로이며 모든 AD 환경의 즉시 침해를 의미하지 않음.

- 영향: Domain Controller account의 directory replication rights가 credential theft blast radius를 확대하는 조건
- 범위: Enterprise CA 구성·Machine template enrollment·patch level·SMB/LDAP network path에 따라 실제 노출 차이
- 경계: 공개 보도는 active exploitation 또는 특정 조직 침해를 확인하지 않으므로 incident 판단에는 조직 telemetry 필요

#### 왜 중요한가

AD CS certificate issuance는 endpoint 기능이 아니라 directory identity control plane임. 공개 PoC 이후 patch compliance만 확인하면 CA template·machine account·certificate issuance·replication activity의 연쇄 evidence를 놓칠 수 있음.

- 패치: CA와 AD CS host의 Microsoft 7월 14일 업데이트 적용·재부팅·version evidence 확인
- 헌팅: 새 computer account, Machine template certificate issuance, PKINIT, DCSync와 `krbtgt` access를 시간순 상관 분석
- 완화: patch 지연 시 chase fallback 비활성화는 정상 enrollment를 손상할 수 있어 lab 검증·change approval·rollback 필요

#### 시사점

인증기관과 도메인 컨트롤러를 같은 recovery scope로 운영하고, certificate template와 CA network egress를 identity attack surface로 관리해야 함.

- 팀 액션: Enterprise CA·AD CS host·template owner·CA firewall rule·machine-account quota의 inventory와 owner 확인
- 팀 액션: certificate issuance와 AD object change 로그를 SIEM에 연결하고 high-privilege template·DC identity alert 추가
- 팀 액션: CA patch 적용 뒤 정상 Machine enrollment와 blocked chase path를 staging에서 재검증

- 시사점: Windows·AD 운영 팀은 CA와 AD CS host의 7월 14일 업데이트를 inventory로 확인하고, Enterprise CA·Machine template·`ms-DS-MachineAccountQuota`·최근 computer-account 생성·비정상 certificate issuance·PKINIT·DCSync를 묶어 hunt 필요. patch 지연 시 vendor/연구자가 언급한 chase fallback 비활성화는 정상 enrollment 영향을 낼 수 있으므로 change window와 rollback을 포함해 검증 필요.
