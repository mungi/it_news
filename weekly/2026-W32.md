각 layer는 해당 PR의 diff만 독립 검토하고, PR 상단 stack map으로 전체 변경 안에서의 위치를 확인하는 방식. 동료가 서로 다른 layer를 병렬 review 가능.

- 병합: 준비된 가장 위 PR을 merge하면 그 아래의 미병합 layer를 한 작업으로 landing 가능

- 보호: 기존 branch protection과 required check가 `main`으로 들어가는 변경에 그대로 적용

#### 사용 경로와 rollout 범위

GitHub는 github.com, GitHub CLI, 모바일 앱, GitHub Copilot의 `gh-stack` skill을 사용 경로로 제시함. CLI extension 설치 명령과 public preview·merge queue rollout 범위를 구분해 안내.

- CLI: `gh extension install github/gh-stack`로 extension 설치 가능
- preview: 모든 저장소에 향후 며칠간 순차 rollout이라는 GitHub 안내
- 경계: stacked PR의 merge queue 지원은 향후 몇 주에 걸친 별도 progressive rollout이며 즉시 전 저장소 제공으로 단정 불가

#### 왜 중요한가

AI-assisted 개발로 change volume이 커지면 review는 품질 gate이자 delivery bottleneck이 됨. stack은 change surface를 작은 순서 단위로 만들지만 dependency와 CI 실행 비용을 자동 해결하지 않음.

- 품질: 작은 diff review와 기존 required check를 결합해 layer별 승인 evidence 보존 가능
- 속도: 독립 layer의 병렬 review로 대형 feature의 feedback loop 단축 가능
- 리스크: base layer 지연·rebase conflict·중복 CI·merge queue 대기가 상위 layer 전체의 delivery lead time으로 전이 가능

#### 시사점

- 팀 액션: stack별 CI duration·queue wait·rebase conflict·review lead time·rollback scope를 단일 PR baseline과 비교

### 31. GitLab Oj Spill 공개 PoC: 프로젝트 push 권한 계정의 Jupyter diff RCE, Webservice 이미지 버전 즉시 점검

핵심: depthfirst 연구와 GitLab 6월 10일 patch release는 self-managed GitLab CE/EE의 `Oj` native C parser 결함 두 개가 crafted `.ipynb` commit diff에서 `git` 사용자 명령 실행으로 연결될 수 있음을 확인. 범위: project에 push 가능한 인증 사용자가 대상이며, GitLab `15.2.0`~`18.10.7`·`18.11.0`~`18.11.4`·`19.0.0`~`19.0.1`과 Oj `3.13.0`~`3.17.1`이 영향 범위로 제시됨. 대응: Webservice image의 실제 GitLab version을 확인해 `18.10.8`·`18.11.5`·`19.0.2` 이상으로 올리고, notebook diff 접근·Puma process·secret 노출 범위를 incident 기준으로 점검 필요.

depthfirst의 기술 공개는 Oj native C parser의 out-of-bounds write와 heap-pointer disclosure를 결합해 기본 GitLab 설치에서 원격 코드 실행에 도달하는 경로를 설명한다. 공격자는 push 권한이 있는 인증 계정으로 crafted Jupyter `.ipynb`를 commit하고 해당 commit diff를 열어 GitLab의 `ipynbdiff`가 Puma worker 안에서 attacker-controlled JSON을 `Oj::Parser.usual.parse`로 처리하게 만든다. 공개 자료는 GitLab CE/EE 모든 tier와 Free·Premium·Ultimate를 범위에 포함하며, 영향 버전은 `15.2.0`~`18.10.7`, `18.11.0`~`18.11.4`, `19.0.0`~`19.0.1`로 열거한다. - 판단: public PoC는 patch 우선순위 신호이며 incident 확정은 `.ipynb` activity와 runtime telemetry로 별도 판정

#### 본문 핵심 포인트

기존 dual-stack 구성은 IP version별 load balancer를 따로 두고 DNS로 client를 나누거나, 하나의 target group에 protocol translation traffic을 보내 원본 client IP를 포기해야 하는 선택지였음. listener rule은 Layer 3에서 조건부 routing을 수행해 이 trade-off를 줄이는 기능임.

- 이전 방식: IPv4·IPv6별 NLB 두 대와 DNS split으로 infrastructure·운영 surface 증가
- 이전 방식: 단일 target group과 protocol translation 사용 시 backend가 original client IP를 잃는 경로
- 적용: 기존 dual-stack NLB를 재생성하지 않고 listener rule 추가 가능
- 지원 listener: TCP·UDP·TCP_UDP·TLS 범위
- 호환: connection draining·target group stickiness·cross-zone load balancing·weighted target group·client IP preservation과 함께 동작

#### 왜 중요한가

원본 client IP는 backend audit, rate limiting, abuse detection, customer network allowlist, trace correlation에서 의미를 가질 수 있음. listener rule은 network topology를 단순화할 수 있으나 IPv6 target group의 application readiness와 health state를 IPv4와 같은 수준으로 운영해야 하는 조건이 생김.

- 보안: client IP 기반 allowlist·rate limit·forensic log가 address translation 뒤에도 일관되는지 확인 필요
- 가용성: IPv6 target group의 health failure가 IPv4 traffic의 fallback과 어떤 관계를 갖는지 failure drill 필요
- 운영: target group별 connection count·reset·healthy host·backend latency를 address family label로 분리 관측 필요

#### 시사점

기능 자체의 추가 요금은 없지만 표준 NLB load balancer hour와 LCU 요금은 적용됨. 승인 기준은 listener rule 생성 성공이 아니라 IPv4·IPv6 client path가 동일한 authentication·logging·latency·rollback SLO를 만족하는지 여부임.

- 팀 액션: IPv4·IPv6 client와 target registration·health check·security group/NACL·application log의 source IP test matrix 작성
- 팀 액션: connection draining·stickiness·cross-zone·weighted target group이 address family별로 예상대로 동작하는지 canary 검증
- 팀 액션: IPv6 backend capacity 부족·health check failure·rule rollback에서 DNS·NLB·application recovery 순서 runbook화
- FinOps: LCU·cross-zone traffic·target group별 capacity와 client IP preservation 요구를 동일 dashboard에서 추적

- 시사점: 네트워크·플랫폼 팀은 listener rule 적용 전 IPv4·IPv6 target group의 health check, target registration, security group/NACL, backend log의 source IP, connection draining, cross-zone traffic, rollback을 같은 test matrix로 검증 필요. 비용은 기능 추가 요금이 아닌 LCU·cross-zone traffic·target group별 capacity와 장애 시 failover 결과로 추적 필요.

### 50. Confidential Containers, CNCF Incubating 승격: Kubernetes에서 TEE·attestation·secret release를 함께 운영하는 data-in-use 보안 경계

CNCF는 Confidential Containers를 incubating project로 승인했다. 이 프로젝트는 Kata Containers runtime과 hardware-based TEE를 Kubernetes workflow에 통합해 data in use를 보호하는 구조를 제시하며, unmodified container 배포, Trustee attestation service, Helm chart·controller, Intel TDX·AMD SEV-SNP를 포함한 hardware abstraction layer를 설명한다. CNCF 게시물의 contributor·repository·issue 수치는 프로젝트 활동 지표이며, 조직별 confidential workload의 성능·key release·운영 복구 특성은 실제 hardware·cloud·policy 조합에서 별도 검증이 필요하다.

#### 무슨 일이 있었나

CNCF Technical Oversight Committee가 Confidential Containers를 incubating project로 승인함. 프로젝트는 cloud-native 환경에서 처리 중인 data in use를 hardware-based Trusted Execution Environment로 보호하는 방향을 제시함.

- 목적: at-rest·in-transit 암호화만으로 보호되지 않는 memory processing 경로의 접근 경계 강화
- 기반: Kata Containers runtime과 Kubernetes workflow를 결합해 public cloud·private infrastructure의 sensitive workload 배포 지원
- 발행: CNCF RSS `pubDate` 2026-07-22 16:00 UTC를 2026-07-23 01:00 KST로 변환

#### 본문 핵심 포인트

CNCF 게시물은 Confidential Containers가 heterogeneous TEE 환경의 hardware isolation을 Kubernetes resource와 controller로 추상화하는 구성을 설명함.

- Pod: unmodified container를 TEE 전반에 배포하도록 Kubernetes Pod resource 경로로 추상화
- Attestation: `Trustee`가 TEE-enabled node·workload integrity를 확인한 뒤 secret·key release를 담당하는 구조
- Lifecycle: Helm chart·controller가 heterogeneous TEE 환경의 confidential workload provisioning·orchestration을 지원
- 하드웨어: Intel TDX·AMD SEV-SNP 등 복수 TEE integration을 hardware abstraction layer로 제시
- 연계: Kyverno integration과 confidential AI use case를 위한 KServe integration 진행 언급

#### 왜 중요한가

TEE 도입은 container encryption option 하나를 추가하는 작업이 아님. node attestation이 성공한 경우에만 secret을 내주고, runtime·firmware·policy·identity를 함께 신뢰해야 하는 control plane 변경임.

- 신뢰 경계: infrastructure operator가 처리 중 data를 직접 읽지 못하게 하는 목적이지만 TEE·attestation·key policy의 정확한 조합에 의존
- 운영 경계: node replacement·firmware update·Kata runtime upgrade에서 attestation failure와 secret re-release 절차 필요
- 성능 경계: CNCF의 project maturity·community activity는 production workload latency·GPU compatibility·isolation overhead를 보증하지 않는 범위

#### 시사점

Confidential Containers의 incubating 승격은 Kubernetes에서 data-in-use protection을 표준 control surface로 다룰 기반이 커졌다는 의미임. 실제 production 승인 기준은 Pod 기동 성공이 아니라 attestation·key release·observability·recovery가 SLO 안에서 작동하는지 여부임.

- 팀 액션: TEE 지원 instance·firmware·cloud region·Kata runtime·device plugin compatibility inventory
- 팀 액션: attestation deny·Trustee unavailable·KMS/key rotation·node replacement에서 workload restart와 secret recovery drill
- 팀 액션: confidential·non-confidential pool의 scheduling, network egress, log·trace redaction, tenant isolation 기준 분리
- 팀 액션: sensitive AI inference는 model artifact·prompt·retrieval data·key custody·audit event를 data path별로 검토

- 시사점: 플랫폼 팀은 confidential workload를 일반 Pod처럼 rollout하기 전에 TEE 지원 node·firmware·Kata runtime·attestation policy·Trustee key release·KMS/secret rotation·node replacement를 하나의 acceptance test로 검증 필요. KServe 연계는 confidential AI use case 방향성일 뿐, 모델 성능·GPU 지원·멀티테넌시·recovery SLO는 환경별로 확인 필요.
