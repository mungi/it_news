### Unbound DNSSEC `CVE-2026-81642`: resolver fleet을 version·DNSSEC·query exposure 단위로 봉쇄

한 줄 결론: Unbound `1.26.0` 이하 DNSSEC validator의 DNSKEY digest heap overflow는 악성 zone 질의에서 DoS와 attacker-controlled data 기반 possible RCE 범위를 가짐. `1.26.1` 또는 vendor backport, recursive exposure 축소, signed-zone canary와 crash·SERVFAIL forensic을 하나의 변경으로 처리해야 함.

- 일일 재검토: 2026-09-18 02:49 KST

#### 한 줄 결론

이 결함은 DNSSEC parser의 메모리 안전성 문제이지만 운영 대응은 DNS daemon patch만으로 끝나지 않음. 취약 version, DNSSEC validation, 외부 재귀 질의, forwarder와 container image를 함께 확인하고 정상·실패 DNS resolution 증거로 배포를 닫아야 함.

- 변화: `CVE-2026-81642`는 Unbound `1.26.0` 이하 DNSKEY digest heap overflow로 공개
- 판정: resolver fleet patch와 query exposure·telemetry 검증을 동일 incident closure로 관리 필요

#### 원문과 관련 뉴스의 핵심 내용

NLnet Labs advisory는 2026-09-16 critical severity로 이 취약점을 게시함. DNSKEY owner compression pointer가 자신의 RDATA를 가리키면 digest buffer overflow가 발생하며, malicious zone을 제어하는 공격자가 vulnerable Unbound의 query를 유도하는 조건이 필요함.

- 영향: denial of service와 attacker-controlled data를 통한 possible remote code execution 범위
- 수정: Unbound `1.26.1`이 decompression 뒤와 write 전에 offending buffer capacity 검사 추가
- 대안: minimal·complete·combined patch와 source-tree manual application 경로 제공
- 경계: advisory는 active exploitation·successful RCE·개별 resolver 노출을 확인하지 않음

#### AI/Infra 전문가 해석

DNSSEC validation은 application Pod 하나가 아니라 shared resolver 또는 node-local DNS, corporate recursive DNS, upstream forwarding chain에서 수행될 수 있음. public listener 하나의 update 누락이 CI, service discovery, external dependency resolution의 공통 failure domain이 될 수 있으므로 asset inventory와 traffic path가 patch 우선순위를 결정함.

- 볼 것: package version뿐 아니라 DNSSEC enablement·listen interface·ACL·forwarder·container image provenance
- 피할 것: CVE severity만으로 internet exposure 또는 local compromise를 확정하는 판단
- 판정: authoritative DNS owner가 아닌 recursive resolver owner와 platform network owner의 공동 approval 필요

#### 아키텍처·운영 관점

악성 zone을 질의하는 경로가 있어야 하므로 external recursive client, untrusted tenant workload, outbound DNS egress, split-horizon forwarder를 구분해야 함. patch 후에도 stale image나 autoscaling node가 old binary를 재도입하면 fleet closure가 깨질 수 있어 immutable image와 restart evidence가 필요함.

- 검증: representative signed zone resolution과 DNSSEC validation success·failure path 비교
- 검증: resolver process version, package backport, deployment image digest, restart time을 asset별 수집
- 운영: public recursive service와 internal management·node-local resolver의 owner와 rollback runbook 분리

#### 보안·SRE·FinOps 관점

원문이 successful RCE를 확인하지 않았으므로 incident scope는 telemetry로 좁혀야 함. crash·core dump·unexpected restart·SERVFAIL·validation error와 unusual zone query를 보존하고, patch canary가 resolver latency·cache hit·upstream retry를 악화시키지 않는지 확인해야 함.

- 보안: advisory date 이후 abnormal query name·DNSSEC validation error·process crash를 hunt 대상으로 지정
- SRE: canary의 query latency·SERVFAIL rate·restart count·upstream timeout을 baseline과 대조
- FinOps: retry-driven upstream DNS traffic과 resolver autoscaling·incident compute cost를 분리 관측

#### 도입 로드맵

첫 단계는 version과 query exposure의 inventory이며, 그 다음 fixed build 적용과 negative/representative resolution test를 병렬 수행해야 함. 서비스 영향이 큰 resolver는 canary cohort로 진행하고 old image 재배포를 막은 뒤 fleet closure evidence를 남겨야 함.

- 1단계: Unbound version·DNSSEC setting·listener ACL·external query path·deployment owner inventory
- 2단계: `1.26.1` 또는 vendor backport 적용과 malicious/invalid input reject test
- 3단계: signed-zone resolution·SERVFAIL·latency·crash telemetry canary와 rollback rehearsal
- 4단계: image drift·autoscaling node·forwarder path 재점검 후 fleet closure 승인

#### 개발팀/인프라팀 체크리스트

DNS 운영, platform engineering, application networking, SOC가 같은 resolver의 역할을 다르게 인식할 수 있음. update ticket에는 binary version뿐 아니라 query client 범위와 observation window를 남겨야 change 완료와 security closure를 동시에 판단할 수 있음.

#### AI/Infra 전문가 해석

agent harness는 model call만 처리하지 않고 tool execution, auth, hooks, workspace state, retries, UI and SDK callback을 연결함. subprocess를 in-process ABI로 바꾸면 startup과 memory path가 달라질 수 있지만 crash isolation, cancellation, backpressure, native library patch cadence도 함께 달라짐.

- 볼 것: process boundary 제거 뒤 failure containment·restart·cancellation·resource limit semantics
- 피할 것: Rust 전환 또는 AI-authored line count를 security·reliability 성과로 바로 해석하는 방식
- 판정: platform owner와 SDK consumer owner가 compatibility matrix와 error budget을 공동 소유 필요

#### 아키텍처·운영 관점

C ABI는 language binding을 넓히지만 memory ownership, thread lifecycle, version negotiation, error translation을 explicit contract로 만듦. shared runtime의 update가 여러 product surface에 전달되므로 feature flag, protocol compatibility, crash reporting, release provenance가 single binary보다 중요한 control plane이 됨.

- 검증: ABI version·memory ownership·callback thread·cancellation·structured error contract
- 검증: tool/auth/telemetry hook, subprocess fallback, socket/stdin-stdout server path의 behavior parity
- 운영: SDK별 supported runtime range, feature flag, crash signature, revert artifact를 release manifest에 기록

#### 보안·SRE·FinOps 관점

in-process embedding은 process startup과 working set을 줄일 가능성이 있으나 blast radius와 observability path도 바꿈. performance claim은 task mix, model latency, tool I/O, cache, host density 조건에 따라 달라져 same-workload measurement 없이는 capacity plan으로 사용할 수 없음.

- 보안: native dependency·FFI input validation·credential callback·tool permission boundary를 별도 review
- SRE: startup, RSS memory, crash/restart, request cancellation, E2E success, tail latency를 cohort별 비교
- FinOps: host density·CPU/RSS·subprocess count·retry rate를 workload unit과 model cost에서 분리 측정

#### 도입 로드맵

migration은 pure helper와 deterministic component부터 시작하고 state owner와 orchestration은 dual implementation 또는 clear rollback boundary가 있을 때 옮기는 편이 안전함. release마다 input/output compatibility와 operational metric threshold를 통과해야 다음 component로 확장할 수 있음.

- 1단계: process·FFI·state·tool permission·telemetry dependency와 consumer inventory
- 2단계: leaf component port, golden/E2E test, error/cancellation behavior parity 검증
- 3단계: prerelease cohort에서 memory·startup·crash·latency·rollback signal 관측
- 4단계: stateful orchestration 확대 전 SDK compatibility·security review·revert rehearsal 승인

#### 개발팀/인프라팀 체크리스트

코드 변경량이 크면 review capacity와 supply-chain 검증도 병목이 됨. codegen 사용 여부와 무관하게 PR provenance, dependency lock, unsafe/FFI review, benchmark harness, release owner가 traceable해야 production decision을 재현할 수 있음.

- 팀 액션: component PR과 deployed release evidence를 same change record로 연결
