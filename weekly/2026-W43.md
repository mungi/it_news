### AWS Transform Azure-to-AWS code conversion: SDK 변환 뒤 service contract를 검증하는 migration 운영 설계

한 줄 결론: Azure SDK에서 AWS SDK로의 .NET code conversion은 migration의 source-level 작업을 줄이지만, storage·queue·database·identity·network·observability의 target contract를 자동으로 이행하지 않음. conversion diff와 behavior evidence를 분리해 승인해야 cutover와 rollback을 관리할 수 있음.

- 일일 재검토: 2026-10-17 01:03 KST

#### 한 줄 결론

AWS Transform의 Azure-to-AWS SDK conversion은 **source code migration을 가속하는 도구**이며 service contract migration의 자동 완성은 아님. compute·storage·queue·database mapping마다 data, identity, retry, operations evidence를 별도 승인해야 함.

- 변화: Azure SDK를 AWS SDK로 바꾸는 .NET cloud-native code conversion 정식 출시
- 팀 액션: generated code diff와 service behavior diff를 같은 migration gate에서 검증

#### 원문과 관련 뉴스의 핵심 내용

AWS는 .NET modernization agent가 submitted source의 Azure service code를 발견하고 assessment report와 modernization plan에서 option을 제공한다고 설명함. Azure Functions→AWS Lambda, Azure Blob Storage→Amazon S3, Azure Queue Storage→Amazon SQS가 지원되며 Azure Cosmos DB→Amazon DynamoDB는 preview로 발표됨.

- 원문 사실: user가 option을 accept 또는 adjust한 뒤 transformation을 실행하는 workflow
- 원문 사실: equivalent AWS SDK call 변환과 transformed code incorporation validation 설명
- 경계: semantic equivalence·data migration·production SLO·security posture를 보장하는 공지 아님

#### AI·Infra 전문가 해석

cloud-native application은 SDK call 외에도 configuration·resource policy·event source·network·observability로 구성됨. code-level mapper가 인간 작업을 줄여도 runtime behavior의 ownership은 application과 platform team에 남음.

- 설계: source service·target service·behavior contract·owner·test evidence를 mapping registry로 관리
- 피할 것: compilation 또는 unit test만으로 storage consistency·queue delivery·failure recovery를 승인

#### 데이터·이벤트 아키텍처 관점

S3 object semantics와 Azure Blob Storage, SQS queue semantics와 Azure Queue Storage, DynamoDB와 Cosmos DB의 schema·partition·query·consistency 모델은 workload마다 다름. event idempotency·serialization·TTL·backup/reconciliation을 conversion diff에서 따로 확인해야 함.

- 검증: object metadata·access·encryption·lifecycle·event trigger의 mapping
- 검증: visibility timeout·retry·duplicate delivery·DLQ·consumer idempotency와 data reconciliation plan

#### identity·보안·운영 관점

Azure managed identity·RBAC·Key Vault·Private Endpoint와 AWS IAM·KMS·Secrets Manager·VPC endpoint는 명칭이 아니라 enforcement boundary가 다름. generated code에 secret value가 없더라도 deploy identity·resource policy·audit route가 빠지면 권한 확대가 생길 수 있음.

- 통제: least privilege IAM·secret retrieval·egress·KMS·CloudTrail을 infrastructure review에 포함
- 통제: target account, environment, policy exception, rollback owner를 wave별로 명시

#### 성능·FinOps 관점

Lambda concurrency와 cold start, S3 request/storage class, SQS polling, DynamoDB capacity는 Azure source의 latency와 billing shape를 보존하지 않을 수 있음. transform adoption은 conversion rate 대신 business transaction success와 unit cost를 기준으로 평가해야 함.

- 측정: p95 latency·error·retry·queue age·throttle·storage request·egress·unit cost cohort 비교
- 리스크: default quota·autoscaling·cross-region data path를 확인하지 않은 전면 cutover

#### 도입 로드맵

stateless, low-risk component에서 mapping evidence를 쌓은 뒤 event workflow와 stateful workload로 확대하는 순서가 안전함. data migration과 code conversion, production traffic shift를 하나의 irreversible step으로 합치지 않아야 rollback 선택지가 남음.

- 1단계: SDK/service inventory, data classification, SLO/RTO/RPO, dependency owner 정의
- 2단계: generated diff와 failure injection을 test account에서 canary 검증
- 3단계: staged traffic 또는 dual-read 후 reconciliation·audit·cost review와 rollback drill

#### 개발팀·인프라팀 체크리스트

개발팀은 behavior regression과 application contract를, 인프라팀은 account·network·identity·telemetry baseline을 소유해야 함. migration change record가 code와 IaC·policy를 모두 가리켜야 incident 때 root cause를 분리할 수 있음.

- 체크: SDK version·mapping·serialization·retry/idempotency·contract test 확인
- 체크: IAM·KMS·VPC endpoint·DNS·secret·logging/alert parity 확인
- 체크: migration wave별 reconciliation·budget·RTO/RPO·rollback evidence 보관

#### 강조 메세지

Azure-to-AWS conversion은 migration의 첫 병목을 줄이지만, 결정적인 위험은 source가 아닌 target 운영 계약에서 발생함. **자동화된 code change와 검증된 service change를 구분**해야 빠른 migration이 복구 가능한 migration이 됨.

- 발표 포인트: three GA service mappings와 Cosmos DB→DynamoDB preview 범위
- 즉시 행동: 대표 .NET service 하나에서 queue/data/identity failure path를 source·target 양쪽으로 test

### 1. AWS Transform, Azure SDK에서 AWS SDK로의 .NET cloud-native 코드 변환 정식 출시

- 발행: 2026-10-16 22:50 KST
- 분류: Cloud | 태그: AWS, AWS Transform, Azure, .NET, Migration, Serverless, Cloud-native
- 출처: [AWS What’s New](https://aws.amazon.com/about-aws/whats-new/2026/10/aws-transform-azure-to-aws-code-conversion/)

핵심: AWS Transform .NET modernization agent가 제출한 source에서 Azure SDK 사용을 찾아 AWS SDK 호출로 바꾸는 기능을 정식 출시함. Azure Functions→Lambda, Blob Storage→S3, Queue Storage→SQS를 지원하며 Cosmos DB→DynamoDB는 preview 범위임; 자동 변환 결과는 API·데이터 모델·비동기 처리·identity·운영 계약을 대체로 보존하지 않으므로 workload별 검증 필요.

AWS 공식 공지는 AWS Transform의 Azure-to-AWS cloud-native .NET code conversion 정식 출시를 발표했다. modernization agent는 제출한 source code에서 Azure SDK를 발견하고 assessment report와 modernization plan에 변환 옵션을 제시하며, 사용자는 옵션을 수락하거나 조정한 뒤 변환을 실행한다. 발표 범위의 변환은 Azure Functions에서 AWS Lambda, Azure Blob Storage에서 Amazon S3, Azure Queue Storage에서 Amazon SQS이며 Azure Cosmos DB에서 Amazon DynamoDB는 preview다. Transform은 identified Azure service code를 equivalent AWS SDK call로 바꾸고 transformed code에 반영됐는지 검증한다고 설명한다. API semantic, data model, consistency, retry, authorization, deployment, observability, cutover 결과까지 자동으로 동등하다고 보장하는 공지는 아니므로 conversion diff와 production contract를 별도 검증해야 함.

#### 무슨 일이 있었나

AWS가 Azure cloud-native .NET application을 AWS로 옮길 때 source-level conversion을 지원하는 AWS Transform 기능을 정식 출시함. source에 남아 있는 Azure SDK 사용 지점을 찾고 AWS service code로 바꾸는 modernization path가 공지 범위.

- 변화: Azure SDK discovery와 conversion option을 assessment report·modernization plan에 제시
- 범위: Azure Functions→AWS Lambda, Blob Storage→Amazon S3, Queue Storage→Amazon SQS 변환 지원

#### 원문에서 확인된 변환 흐름

사용자는 modernization plan에서 제시된 conversion option을 수락하거나 선호에 맞게 조정한 뒤 transformation을 실행함. Transform은 식별한 Azure service code를 equivalent AWS SDK call로 변환하고 transformed code 반영 여부를 검증한다고 설명함.

- 확인: source discovery·option review·transformation·incorporation validation의 순서
- 경계: compile 성공 또는 SDK call 교체가 end-to-end production behavior 동등성을 보장하는 발표 아님

#### 데이터·메시징 계약

storage와 queue service 이름이 대응하더라도 data model·partitioning·consistency·retention·delivery·ordering·dead-letter behavior는 application contract의 일부임. Azure Cosmos DB→DynamoDB mapping은 preview이므로 production migration 전 workload evidence가 특히 필요함.

- 검토: blob object key·metadata·access policy와 S3 encryption·lifecycle·event notification 차이
- 검토: queue visibility timeout·retry·duplicate delivery·DLQ·consumer idempotency를 service별로 재검증

#### identity·보안·배포 관점

SDK 변환은 managed identity, Azure RBAC, Key Vault reference, network endpoint, CI credential, audit log을 IAM·KMS·VPC endpoint·CloudTrail로 자동 등가화하지 않음. runtime code와 infrastructure policy가 다른 repository에 있으면 privilege drift가 남을 수 있음.

- 통제: least-privilege IAM policy·secret retrieval·egress·resource policy를 generated diff와 별도 review
- 통제: deploy identity·artifact provenance·environment variable·audit event를 migration wave별로 확인

#### 성능·비용 관점

Lambda concurrency, S3 request·storage class, SQS polling, DynamoDB capacity model은 Azure 원본의 latency와 billing shape를 그대로 재현하지 않을 수 있음. conversion 완료 지표 대신 representative load의 p95 latency·error·retry·unit cost를 같은 dashboard에서 비교해야 함.

- 측정: cold start·concurrency throttling·queue age·retry·storage request·egress를 pre/post cohort 비교
- 리스크: target service default limit과 autoscaling 설정을 확인하지 않은 채 source 변환 성공을 migration 완료로 해석

#### 도입 로드맵

먼저 service inventory와 non-functional contract를 만들고 stateless·low-risk component에서 generated diff를 검증한 뒤 stateful data와 event workflow로 확장해야 함. cutover와 rollback은 code 변환 단계와 독립된 release decision으로 관리 필요.

- 1단계: Azure SDK·service dependency·data classification·SLO·rollback owner inventory
- 2단계: representative request와 failure injection으로 generated code·IAM·event behavior canary
- 3단계: shadow/dual-read 또는 staged traffic migration 뒤 data reconciliation·cost·audit evidence review

#### 개발팀·인프라팀 체크리스트

개발팀은 mapping table과 behavior regression을, 플랫폼팀은 account·network·identity·observability baseline을 소유해야 함. code conversion을 IaC, security control, data migration과 한 pull request로 묶으면 rollback 원인이 불명확해질 수 있음.

- 체크: migration wave별 RTO/RPO·data reconciliation·budget·rollback exercise 기록

agent가 reasoning loop마다 작은 memory event를 기록·조회하면 token invoice 외의 memory cost가 누적될 수 있음. 12KB minimum은 작은 event의 effective price를 키울 수 있고, long TTL은 replay·debug 목적의 보존과 비용·privacy trade-off를 만듦.

- 리스크: small event fragmentation으로 ingestion/retrieval billable floor 비율이 높아지는 경로
- 리스크: retrieval policy가 넓어져 stale context·latency·비용을 동시에 늘리는 경로

#### 시사점

memory 저장을 기본 기능으로 두지 말고 task state·audit evidence·retrieval corpus를 분리해야 함. trace별 payload byte와 access 패턴을 계측한 뒤 compaction·TTL·retrieval budget을 prompt/tool release와 함께 조정할 필요가 있음.

- 팀 액션: event-size histogram·floor hit rate·retrieve-to-ingest ratio·TTL·agent당 비용 dashboard 구성
- 팀 액션: short/long-term memory별 retention·delete·access control과 context compaction canary 검증

- 시사점: 시사점: memory event의 byte histogram·12KB floor 적용 비율·retrieve-to-ingest ratio·TTL·session length·agent당 storage와 total cost를 trace별로 기록하고, context compaction과 retrieval budget을 함께 설정 필요.

- 대상: SIEM·analytics platform·object storage로 전달하는 Cloudflare log stream

- 팀 액션: incident investigation용 immutable raw evidence의 보존 위치와 접근 승인을 별도 설계

- 시사점: 시사점: source field inventory·destination allowlist·query digest·test fixture·approval owner·rollback query를 같은 change record에 보존하고, drop rate·parse failure·delivery lag·alert coverage를 canary 기준으로 비교 필요.
