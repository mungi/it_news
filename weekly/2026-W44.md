### llm-d v1.0.0: 분산 추론을 모델 배포가 아닌 SLO·capacity control plane으로 운영하는 방법

한 줄 결론: llm-d v1.0.0은 priority·fairness-aware flow control, router HA, prefill/decode coordinated rollout, session affinity를 묶어 agent 추론 fleet의 운영 기능을 확장함. 성능 주장은 workload·가속기·model server·traffic mix에 종속되므로, v1 전환은 image·CRD·routing policy·rollback을 함께 검증하는 platform release로 다뤄야 함.

- 일일 재검토: 2026-10-21 02:48 KST

#### 한 줄 결론

`llm-d v1.0.0`의 검토 단위는 inference server 설치 여부가 아니라 **tenant별 SLO·queue·cache·capacity를 제어하는 release**임. agent workload의 burst와 multi-turn locality를 다루는 기능이 추가됐지만, target model·GPU·traffic mix에서의 latency와 비용은 별도 검증이 필요함.

- 변화: priority·fairness-aware flow control, router HA, `DisaggregatedSet`, session-aware serving을 v1 release에 결합
- 팀 액션: upgrade 승인 전에 admission·queue·p95 latency·cache hit·GPU utilization·rollback 지표의 owner와 임계값 확정

#### 원문과 관련 뉴스의 핵심 내용

GitHub release는 multi-tenant QoS에서 probabilistic admitter, program-aware fairness, turn-priority scoring을 포함한 controlled load shedding과 `flowControl` 설정 통합을 명시함. router는 hot standby와 safe rolling update를 지원하고, `DisaggregatedSet`은 prefill/decode replica의 coordinated rollout·lockstep upgrade·Pod snapshot readiness·native revision routing을 다루는 범위임.

- 원문 사실: router configuration API가 `v1`으로 승격되고 Responses API가 `previous_response_id` 지원
- 원문 사실: session-state-producer plugin과 evolving session affinity로 multi-turn cached context 근접 배치 지향
- 원문 사실: DRA/DRANET topology-aware accelerator guide와 `llm-d-pd-utils`의 GPU topology·network benchmark 지원 추가

#### AI·Infra 전문가 해석

agent serving에서 request rate만으로 autoscaling하면 cached prefix가 있는 replica와 멀어지거나 queue가 과도하게 늘 수 있음. priority와 fairness는 product policy이며, admission은 SRE safety valve임. 따라서 router가 정한 placement·drop·retry 결과를 application trace와 tenant contract에 연결하지 않으면 QoS 개선 여부를 판정하기 어려움.

- 설계: interactive, background, batch를 별 queue·budget·deadline으로 분리하고 tenant·model·session attribute를 routing telemetry에 연결
- 피할 것: controlled load shedding을 장애로 간주해 무제한 retry하거나, fairness 정책을 고객별 quota·계약과 분리
- 판정: accepted·shed·timeout·retry request를 한 trace ID로 기록해 admission 변경 전후 비교

#### 아키텍처·운영 관점

prefill/decode disaggregation은 replica lifecycle과 failure domain을 늘림. `DisaggregatedSet`의 coordinated update가 있어도 model image, tokenizer, cache schema, network fabric, LeaderWorkerSet·Gateway API CRD, routing config가 같은 compatibility envelope에 있어야 함. Pod snapshot readiness는 application readiness와 client-visible SLO를 자동으로 증명하지 않음.

- 검증: canary에서 prefill·decode pair failure, in-flight request drain, revision routing, cache warmup, scale-from-zero를 재현
- 검증: DRA/DRANET placement와 GPU topology·network benchmark 결과를 실제 collective·TTFT·TPOT trace와 대조
- 운영: change record에 image digest·chart·CRD·router policy·model server version·rollback pointer를 함께 보존

#### SRE·FinOps 관점

session affinity와 prefix-cache routing은 cache reuse를 높일 수 있지만 hot session concentration, stale capacity, cross-zone traffic, tail queue를 만들 수 있음. prefill/decode를 분리하면 각 pool의 utilization과 cost attribution도 달라짐. 평균 token cost나 aggregate throughput만으로는 user-facing degradation을 찾기 어려움.

- 측정: tenant·model·queue별 TTFT, TPOT, p95/p99 latency, shed rate, retry rate, cache hit, GPU duty cycle, token당 비용
- 측정: prefill/decode pool별 idle time·queue depth·cross-zone traffic·cache eviction·warmup 비용
- 경계: 릴리스는 조직별 비용 절감, 처리량, 무중단 성공률 또는 SLO 충족 수치를 제시하지 않은 범위

#### 보안·거버넌스 관점

v1에는 model server image와 ecosystem component의 정렬 변경이 포함됨. release notes는 `llm-d-rocm` 자체 image stream을 deprecated로 두고 upstream vLLM image 이동을 예고함. image provenance, signature, vulnerability response, registry access와 tenant data path는 routing 기능과 독립된 배포 통제 대상임.

- 통제: API version·CRD migration·rollback 시 data plane 권한과 secret scope가 확대되지 않는지 review

먼저 한 model·한 tenant tier·read-only workload에서 baseline을 고정하고 router policy만 shadow mode로 비교하는 방식이 안전함. 다음으로 prefill/decode canary와 HA switchover를 실시하고, upgrade 중 in-flight traffic·cache warmup·fallback server가 SLO를 만족하는지 확인해야 함. multi-tenant fairness는 계약 priority와 incident policy가 정해진 뒤 확대해야 함.

개발팀은 session state와 retry semantics를, 플랫폼팀은 routing·capacity·version matrix를, SRE는 SLO·rollback·incident handoff를 공동 소유해야 함. Responses API state를 사용하는 application은 `previous_response_id`의 state lifecycle과 privacy boundary를 별도로 설계할 필요.

### 1. Cloudflare, PHP `php2shell` 취약점 2건의 기본 WAF 보호 배포 공개

- 발행: 2026-10-21 22:56 KST
- 분류: Security | 태그: PHP, php2shell, CVE-2026-109618, CVE-2026-109619, Cloudflare, WAF, Web Security
- 출처: [Cloudflare Blog](https://blog.cloudflare.com/php-vulnerabilities-waf-protection/)

핵심: Cloudflare가 PHP 5.4 이상 웹 서버에 영향을 줄 수 있는 `CVE-2026-109618`·`CVE-2026-109619`의 기본 WAF 보호를 2026-10-21 03:02 UTC부터 배포했다고 공개함. WAF는 request와 origin response signal을 함께 쓰는 완화 계층이며, PHP runtime patch·배포 image 교체·workload restart를 대신하지 않음.

Cloudflare는 Calif.io·Wiz·OpenAI·Quarkslab과의 coordinated disclosure에서 PHP 런타임 `php2shell` 취약점 2건이 공개됐다고 설명함. specially crafted HTTP traffic 처리 시 memory-safety 결함으로 DoS·remote code execution·data exposure가 가능할 수 있으며, PHP 5.4 이상 web server가 영향 범위임. Cloudflare는 공개 약 9시간 전 WAF mitigation을 배포하고 Free·paid WAF 고객에 기본 보호를 적용했으나, application code·plugin만 업데이트해서는 해결되지 않으며 origin PHP software patch가 필요하다고 명시함.

#### 무슨 일이 있었나

Cloudflare가 `php2shell`로 지칭한 PHP runtime 취약점 두 건의 WAF 보호 배포를 공개함. 공개 원문은 specially crafted HTTP traffic 처리 시 PHP 5.4 이상 web server에서 denial of service·remote code execution·data exposure 가능성을 설명하는 범위임.

- 식별자: `CVE-2026-109618`과 `CVE-2026-109619`
- 영향 조건: PHP runtime이 specially crafted HTTP traffic을 처리하는 internet-facing application 경로

#### 취약점·패치 범위

원문은 memory pressure 또는 fatal error 처리 뒤 PHP가 초기화되지 않았거나 해제된 memory를 참조하는 흐름을 설명함. 웹 애플리케이션 코드나 plugin만의 update가 아니라 실행 중인 PHP software update가 필요한 취약점 범위임.

- 영향: PHP process crash·sensitive data exposure·attacker-provided code execution 가능성
- 대상: WordPress·Magento 같은 PHP 기반 application도 origin runtime patch 대상

#### Cloudflare 완화 범위

Cloudflare는 coordinated disclosure 과정에서 10월 초부터 WAF mitigation을 배포했고 2026-10-21 03:02 UTC부터 WAF 사용 Free·paid plan 고객에 default protection을 적용했다고 밝힘. request만 보지 않고 origin response signal을 결합하는 full transaction detection이 첫 managed detection 적용 사례라는 설명임.

- 완화: matching origin response를 requester에 전달하기 전 차단하는 WAF rule 범위
- 관측: 공개 전 정보 유출 뒤 공격 traffic과 payload mutation을 관측한 범위

#### 시사점

WAF event는 edge 경로의 탐지 증거일 뿐 origin patch 완료 증명이 아님. CDN 밖 public endpoint, internal ingress, direct origin address, 서로 다른 container image와 FPM worker를 포함해 runtime asset과 restart state를 확인해야 함.

- 팀 액션: endpoint·runtime version·image digest·WAF coverage·owner·last restart의 patch inventory 작성
- 팀 액션: vendor update 뒤 canary request·error/memory metric·WAF event·origin log를 대조하고 rollback과 incident escalation 조건 검증

- 시사점: 시사점: public PHP endpoint별 runtime version·container/base image·FPM/worker process·WAF coverage·origin access log·last restart를 inventory로 연결할 것. vendor security update 적용 뒤 canary request, error rate·memory·process restart, WAF event와 origin log를 대조하고 Cloudflare 밖 endpoint도 별도 patch completion 기준으로 관리할 것.

DRA는 bare accelerator count 대신 accelerator와 이를 공급하는 network interface의 관계 같은 구조화된 resource claim을 scheduler가 읽도록 하는 방향이며, 일부 DRA-aware autoscaler가 같은 정보를 capacity simulation에 사용하기 시작했다고 기록함. 이는 CNCF 표준 공지나 모든 cluster autoscaler의 기능 발표가 아니라 member post의 architecture 해설이므로 implementation·version·provider별 지원과 실제 scale-up 결과는 별도 canary로 검증해야 함.

#### 무슨 일이 있었나

CNCF member post가 AI accelerator workload에서 scheduler와 autoscaler의 전통적 분업이 만나는 지점을 설명함. node가 존재할 때 배치하는 scheduler와 배치 불가 때 node를 추가하는 autoscaler가 같은 placement 제약을 보지 못할 수 있는 문제임.

- 증상: 지역 전체 capacity 부족이 아니어도 autoscaler가 추가 가능한 node와 scheduler가 사용할 node가 달라 pod pending 발생 가능성
- 경계: CNCF 프로젝트의 새 표준 또는 모든 autoscaler 구현체의 기능 제공 공지가 아닌 member post 범위

#### reservation과 topology

예약 capacity는 이미 비용을 지불한 accelerator를 실제 scale-up에서 사용해야 하는 운영 제약임. topology는 device 수가 아니라 local NUMA CPU·memory, PCIe 경로의 NIC, peer accelerator fabric, rack·data center locality를 함께 다루는 배치 조건임.

- 운영: reservation 소비 여부와 unreserved fallback을 scale-up decision 및 비용 보고에 연결
- 성능: multi-node model은 rack·fabric locality까지 영향을 받으므로 GPU count만으로 all-reduce 경로를 판단하지 않음

#### DRA와 지원 경계

글은 DRA가 bare count 대신 accelerator와 연결 NIC처럼 관계를 포함한 structured claim을 표현하게 한다고 설명함. scheduler는 claim을 읽고 일부 DRA-aware autoscaler는 capacity simulation에 같은 정보를 사용하기 시작했으나 지원 범위는 구현체마다 다름.

- 확인: Kubernetes version·driver·scheduler·autoscaler·provisioner별 DRA claim 및 topology 처리 범위 검증
- 피할 것: DRA API 존재를 GPU placement 최적화·capacity 확보·성능 향상의 자동 보장으로 해석

#### 시사점

AI cluster scale-out은 node 증설 이벤트가 아니라 placement contract의 end-to-end 검증 대상임. queue와 fleet utilization을 함께 개선하려면 scheduler event와 provisioner simulation, reservation, device topology, training throughput을 같은 관찰 단위로 연결해야 함.

- 팀 액션: pending reason·node template·reservation ID·DRA claim·device/NIC topology·queue time을 workload trace에 기록
- 팀 액션: representative distributed job으로 placement locality·scale-up time·idle GPU·all-reduce throughput·cost를 canary 비교

- 시사점: 시사점: GPU workload별 accelerator·CPU/NUMA·NIC·fabric·reservation·DRA claim·node pool·scheduler event를 같은 trace로 수집할 것. DRA 또는 topology-aware provisioning 도입 전에는 pending reason, scale-up simulation, reservation consumption, placement locality, all-reduce throughput, queue time, cost를 canary job으로 비교할 것.

### 16. Google 연구팀, open-world agent용 재귀 self-improvement 프레임워크 `Harness²` 공개

- 발행: 2026-10-19 18:01 KST
- 분류: AI | 태그: Google Research, AI Agent, Agent Harness, Recursive Self-Improvement, Benchmark, AI Safety, Evaluation
- 출처: [AI타임스](https://www.aitimes.com/news/articleView.html?idxno=216410)

핵심: Google Research가 공개한 `Harness²`는 ground-truth verifier가 없는 open-world task에서 agent harness를 task-level과 harnessing-level의 두 단계 재귀로 개선하는 연구 프레임워크임. arXiv는 GLM-5·Gemini 3.5 Flash의 base harness 대비 WorkBuddy-Bench 최대 **11.5점**, JobBench 4.5점, LAB 11.8 percentage point 개선을 보고했으나, 세 professional benchmark와 네 model-harness configuration의 연구 결과이므로 production agent의 일반 성능·안전성·비용 개선을 보장하지 않음.

`Harness²`는 task-level recursion에서 ground-truth verifier 없이 contrastive Propose-Probe-Compose 절차로 현재 task의 harness edit를 유도하고, parallel 또는 sequential recursion으로 예산을 늘릴 수 있다고 설명함. harnessing-level recursion은 task edit 경험을 continual improvement harness에 반영해 이후 새로운 task 적응을 노림. 논문은 세 professional benchmark와 네 model-harness configuration에서 single step 개선 및 task-level recursion budget 증가에 따른 추가 향상을 보고함. 그러나 online harness edit는 prompt·tool·policy·memory·routing의 행동을 바꿀 수 있어 benchmark score와 별도로 write 권한, prompt injection, cost explosion, regression, rollback, audit trace를 release control로 검증해야 함.

#### 무슨 일이 있었나

Google Research가 `Harness²`를 공개했고, AI타임스는 19일 KST 관련 연구를 보도함. arXiv 원문은 LLM agent capability가 base model뿐 아니라 execution harness에 의존하며, open-world 환경의 recursive self-improvement 문제를 다룬다고 설명함.

- 구성: task-level recursion과 harnessing-level recursion을 연결한 plug-and-play framework
- 문제: 설계 때 보지 못한 task와 test-time novelty 때문에 online harness edit를 ground-truth verifier로 유도하기 어려운 조건

#### 방법과 측정 결과

task-level recursion은 contrastive `Propose-Probe-Compose` 단계로 현재 task harness를 개선하고 parallel 또는 sequential recursion 확장이 가능하다고 제시함. harnessing-level recursion은 task edit 경험을 continual improvement harness에 반영하는 구조임.

- 결과: WorkBuddy-Bench 최대 **11.5점**, JobBench 4.5점, LAB 11.8 percentage point 개선이라는 논문 보고
- 조건: 세 professional benchmark와 네 model-harness configuration, GLM-5·Gemini 3.5 Flash base harness 비교 범위

#### 평가 경계와 운영 위험

연구의 score 상승은 production tool call, external write, sensitive data, incident handling에서의 성공률·비용·안전성을 자동 증명하지 않음. verifier가 없는 환경에서 harness edit가 prompt, tool routing, memory, policy를 바꾸면 hidden regression과 권한 확대가 발생할 수 있음.

- 경계: benchmark 개선을 모델 일반 우위나 autonomous production deployment 근거로 확대하지 않을 것
- 리스크: self-improvement edit가 prompt injection, tool misuse, cost increase, stale memory, policy bypass를 새 경로로 만들 가능성

#### 시사점

self-improving agent의 control plane은 model output보다 change evidence가 중요함. candidate edit를 sandbox·read-only task에서 probe하고, holdout evaluation과 human approval을 거쳐 canary로 배포하며, metric regression 또는 policy violation 때 이전 harness로 돌아갈 수 있어야 함.

- 팀 액션: harness diff·task context·probe evidence·model/tool version·IAM scope·cost·approval·rollback을 trace로 보존
- 팀 액션: frozen baseline과 holdout task로 quality·latency·tool cost·policy violation을 함께 비교
- 팀 액션: external write는 idempotency·approval·compensation path가 있는 canary 뒤에만 적용

- 시사점: 시사점: harness self-improvement는 read-only·sandbox task에서 시작하고, edit diff·task context·probe outcome·tool/IAM scope·cost·safety policy decision·human approval·rollback 결과를 append-only trace로 보존해야 함. holdout task와 frozen baseline 없이 online edit를 production write path에 연결하지 말 것.
