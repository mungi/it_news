## Deep Dive

### GuardDuty Runtime Monitoring 선택형 규칙: dry-run을 탐지 운영 계약으로 만드는 방법

한 줄 결론: GuardDuty Runtime Monitoring의 50여 개 선택형 규칙은 탐지 coverage를 넓히지만, 실제 위험 감소는 rule enablement가 아니라 dry-run·triage·containment·증거 보존이 닫힌 운영 loop로 연결될 때만 확인됨. EC2·EKS·ECS별 baseline과 response owner를 먼저 고정해야 함.

- 일일 재검토: 2026-10-20 02:11 KST

#### 한 줄 결론

선택형 runtime rule의 성공 지표는 finding 수가 아니라 **탐지부터 containment와 evidence closure까지의 시간**임. dry-run은 설정 전 미리보기 기능이 아니라 asset·identity·runbook·조사 용량을 검증하는 release stage로 다뤄야 함.

- 변화: AWS가 Runtime Monitoring용 선택형 규칙 **50여 개**와 dry-run 제공
- 팀 액션: rule enablement마다 owner·asset scope·triage SLA·suppression expiry를 change record에 결합

#### 원문과 관련 뉴스의 핵심 내용

AWS 공식 RSS는 process·file·network activity를 다루는 50개 이상 규칙을 공개하고 `sudoers` 변경과 audit logging 비활성화를 환경 의존 신호의 예시로 제시함. 대상은 EC2, EKS, ECS의 EC2·Fargate workload이며 모든 상용 리전과 AWS GovCloud(US) 제공 범위임.

- 원문 사실: 13개 finding type이 persistence·privilege escalation·execution·defense evasion·discovery·exfiltration·command and control 전술과 매핑
- 원문 사실: SuspiciousCommand 2종과 SensitiveFileRead 2종 등 신규 finding type 4개 추가

#### AI·Infra 전문가 해석

runtime rule은 static policy보다 workload 문맥에 가깝지만, rule match만으로 malicious intent를 확정하지 못함. 같은 file read나 command가 deployment·debug·backup·sidecar lifecycle에서는 정상일 수 있으므로 detector와 adjudication을 분리해야 함. 탐지 도입은 security product toggle이 아니라 observation contract를 만드는 작업임.

- 설계: finding에 rule ID·asset·image digest·identity·parent process·command/file/network evidence·deployment revision 결합
- 피할 것: MITRE mapping 또는 rule 개수를 detection coverage와 incident-response 품질의 동의어로 취급

#### 아키텍처·운영 관점

EC2, EKS, ECS는 실행 단위와 owner가 다르므로 같은 finding type도 대응 경로가 달라짐. EKS는 pod·node·service account·image digest·namespace를, ECS는 task definition·task role·container image·cluster를, EC2는 instance profile·AMI·process tree를 함께 남겨야 조사 가능한 사건 단위가 됨.

- 검증: dry-run finding을 CloudTrail·deployment event·image provenance·network flow와 correlation 가능한지 확인
- 운영: workload update, scheduled job, emergency admin action을 변경 캘린더와 연결해 정상 activity 판정 근거 보존

#### 보안·거버넌스 관점

sensitive file read나 suspicious command는 credential·개인정보·운영 명령의 메타데이터를 포함할 수 있음. alert viewer와 containment operator, exception approver의 권한을 분리하고, suppression은 사유·승인자·만료·재검토가 있는 time-bound exception으로 관리해야 함.

- 통제: high-impact finding에는 least privilege, credential rotation, workload isolation, immutable evidence 절차 연결
- 통제: suppression을 permanent allowlist로 바꾸지 않고 expiry 뒤 재평가하도록 workflow화

#### SRE·FinOps 관점

탐지 활성화는 telemetry, finding triage, incident response의 비용과 인력 queue를 함께 늘릴 수 있음. alert 감소만 최적화하면 blind spot이 커질 수 있으므로 coverage, true-positive sample, response time, repeated finding, suppression churn을 함께 봐야 함. dry-run 기간은 production SLO와 보안 운영 용량을 맞추는 관찰 창임.

- 측정: rule별 alert volume·sampled true-positive·MTTA·MTTR·suppression expiry·coverage gap·cost
- 경계: AWS 공지는 조직별 false-positive rate, breach reduction, auto-remediation 결과를 제시하지 않은 범위

#### 도입 로드맵

먼저 critical workload 한두 개에서 asset mapping과 on-call owner를 확정하고 dry-run으로 baseline을 수집해야 함. 이후 credential access 또는 defense evasion처럼 impact가 큰 finding부터 live detection canary를 적용하고, incident drill로 closure evidence를 확인한 뒤 다른 account·cluster로 넓히는 순서가 안전함.

- 1단계: EC2·EKS·ECS workload inventory와 runtime monitoring coverage·owner·log retention 확인
- 2단계: dry-run sample을 rule별로 분류하고 expected admin/deployment behavior와 비교
- 3단계: high-confidence finding canary, escalation, containment, post-incident review를 통한 scope 확장

#### 개발팀·인프라팀 체크리스트

개발팀은 image·deployment·service identity의 provenance를, 플랫폼팀은 telemetry·asset correlation·on-call routing을, 보안팀은 rule lifecycle과 incident close criteria를 함께 소유해야 함. detector가 의미 있는 action으로 이어지려면 release metadata와 runtime evidence의 연결이 필수임.

- 체크: rule ID·finding type·asset/image digest·identity·evidence·owner·triage outcome 기록
- 체크: EKS/ECS/EC2별 coverage gap, stale workload, log retention, regional enablement 확인
- 체크: suspicious command와 sensitive file read scenario의 containment·rotation·forensic drill 실행

#### 강조 메세지

Runtime Monitoring은 rule catalog를 켜는 일이 아니라 **실행 중인 workload의 이상 행동을 닫힌 incident loop로 바꾸는 일**임. 이번 주에는 critical service 하나에서 dry-run finding이 alert·owner·evidence·containment까지 어떻게 흘러가는지 측정해야 함.

- 발표 포인트: 50여 개 선택형 규칙, 13개 finding type, dry-run 제공과 적용 경계
- 즉시 행동: 대표 workload의 dry-run 1주 baseline과 live-detection canary 기준 수립

### Harness²: verifier 없는 open-world agent self-improvement를 release control로 운영하는 방법

한 줄 결론: Harness²는 verifier 없는 open-world task에서 agent harness를 재귀적으로 개선하는 연구 접근을 제시하지만, online edit의 가치는 benchmark score가 아니라 change evidence·권한 경계·rollback이 닫힌 control plane에서 판단해야 함.

- 일일 재검토: 2026-10-20 02:17 KST

#### 한 줄 결론

Harness self-improvement의 통과 기준은 benchmark 점수 하나가 아니라 **candidate edit가 안전한 권한·비용·rollback 경계 안에서 재현되는가**임. verifier 없는 task에서 online edit를 곧바로 production write path에 연결하면 개선 loop가 새 failure mode가 될 수 있음.

- 변화: task-level과 harnessing-level의 두 재귀를 연결한 `Harness²` 공개
- 팀 액션: edit proposal·probe·approval·deployment·rollback을 단일 change ID로 연결

#### 원문과 관련 뉴스의 핵심 내용

arXiv는 open-world task가 harness 설계 시점에 unseen이고 test-time에 novel하므로 ground-truth verifier가 online edit를 안정적으로 안내하기 어렵다고 문제를 정의함. task-level recursion은 contrastive Propose-Probe-Compose로 current task harness를 다듬고, harnessing-level recursion은 그 경험을 continual improvement harness에 반영하는 방식임.

- 원문 사실: parallel 또는 sequential recursion으로 task-level budget을 확장할 수 있는 구조
- 원문 사실: GLM-5·Gemini 3.5 Flash와 네 model-harness configuration에서 세 professional benchmark 측정

#### AI·Infra 전문가 해석

harness는 prompt template, planner, memory, tool routing, retry, evaluator, policy를 묶은 executable control plane임. 따라서 edit가 score를 높여도 tool 선택·data path·retry 폭증·권한 상속을 바꿀 수 있음. candidate generator와 safety/quality adjudicator를 분리하고, holdout evaluation을 online task feedback과 혼동하지 않아야 함.

- 설계: editable harness component와 immutable policy boundary·tool allowlist·budget limit을 분리
- 피할 것: current task probe 성공을 unseen workload의 safety·quality generalization으로 해석

#### 아키텍처·운영 관점

online harness edit에는 input context, proposed diff, probe environment, tool result, model version, memory snapshot, policy decision, deployment target, rollback pointer가 필요함. 이 정보가 없으면 언제 어떤 edit가 external action·latency·cost·failure를 바꿨는지 재현할 수 없음. sandbox와 production connector는 별도 identity·network·secret boundary를 가져야 함.

- 검증: read-only sandbox에서 edit 전후 task success·p95 latency·tool call·token cost·policy violation 비교
- 운영: diff promotion은 feature flag·canary cohort·automatic rollback threshold를 가진 release workflow로 관리

#### 보안·거버넌스 관점

self-improving loop는 untrusted task content가 future harness behavior에 영향을 주는 memory-poisoning 경로가 될 수 있음. probe feedback과 retrieved content를 trusted policy input으로 승격하지 말고 provenance와 isolation을 유지해야 함. external write와 credential scope는 improvement engine과 분리된 approval path가 필요함.

- 통제: edit artifact·retrieval source·tool transcript의 provenance·hash·retention period 기록
- 통제: secret access·SaaS write·cloud mutation은 human approval과 idempotency·compensation으로 분리

#### SRE·FinOps 관점

recursion budget이 늘면 candidate 수, model calls, tool calls, evaluator runtime, queue latency가 함께 증가함. 평균 score만 보면 tail cost와 failure retry를 놓칠 수 있으므로 cost per accepted improvement, p95 task latency, rollback rate, regression rate를 같은 dashboard에서 관찰해야 함.

- 측정: accepted edit rate·holdout win rate·p95 latency·tool/token cost·rollback·policy violation·human rework
- 경계: 논문의 최대 개선 폭은 조직별 workload cost·SLO·reliability 보장 수치가 아님

#### 도입 로드맵

먼저 deterministic 또는 known-answer read-only task에 frozen baseline과 independent check를 둔 뒤, limited sandbox에서 task-level edit만 canary로 시험해야 함. 이후 holdout task에서 benefit이 유지되는지 확인하고, write action은 별도 approval·rollback·incident drill을 통과한 component에만 허용하는 순서가 필요함.

- 1단계: editable component·immutable policy·tool scope·budget·owner inventory화
- 2단계: sandbox probe와 holdout evaluation으로 edit admission criterion 설정
- 3단계: canary, feature flag, rollback SLO, security review를 통과한 제한 workload 확대

#### 개발팀·인프라팀 체크리스트

개발팀은 harness diff와 test artifact를, 플랫폼팀은 isolated runtime·identity·quota·telemetry를, 보안팀은 policy boundary와 approval evidence를 공동 관리해야 함. continual learning state는 일반 application configuration보다 높은 change risk를 가질 수 있음.

- 체크: prompt/model/tool/evaluator/memory/policy version과 task context·probe result 보존
- 체크: read-only/ write tool 분리, egress allowlist, secret isolation, per-run budget 확인
- 체크: regression·timeout·policy violation·budget exhaustion의 rollback과 human handoff drill 실행

#### 강조 메세지

Harness²의 발표 포인트는 self-improvement 자체가 아니라 **verifier 없는 변화도 probe와 경험 축적으로 다루려는 구조**임. 실제 배포에서는 model이 만든 edit보다 조직이 증명할 수 있는 approval·trace·rollback 경계를 먼저 만들어야 함.

- 발표 포인트: WorkBuddy-Bench 최대 11.5점, JobBench 4.5점, LAB 11.8 percentage point의 연구 조건
- 즉시 행동: 대표 read-only agent 한 개에 frozen baseline·holdout·edit trace·rollback threshold 적용

### 2. EC2 Image Builder, 기존 Auto Scaling Group 인스턴스로 이미지 빌드 지원

- 발행: 2026-10-20 02:30 KST
- 분류: Cloud | 태그: AWS, EC2 Image Builder, Auto Scaling, AMI, CI/CD, Platform Engineering
- 출처: [AWS What’s New](https://aws.amazon.com/about-aws/whats-new/2026/10/ec2-image-builder-asg-faster-builds/)

핵심: EC2 Image Builder가 기존 Auto Scaling Group(ASG)의 실행 중인 인스턴스를 image build에 쓰도록 지원함. build 시 새 인스턴스 launch·bootstrap 시간을 줄이고, 사용된 인스턴스는 ASG가 보충하는 pool 방식임. opt-in 기능이며 ASG를 설정하지 않은 기존 pipeline의 기본 launch path는 바뀌지 않음.

EC2 Image Builder가 image build에 기존 Auto Scaling Group의 실행 중인 EC2 instance를 사용할 수 있게 됨. 새 instance launch와 bootstrap 대기 시간을 없애 build를 빠르게 하려는 기능 범위임.

#### Pool 동작과 호환성

AWS는 build에 instance가 사용되면 ASG가 pool을 계속 replenishment해 다음 pipeline run용 instance를 확보한다고 설명함. ASG를 설정하지 않은 pipeline은 기존 default launch path를 계속 사용하므로 기능을 켜지 않은 workload의 동작은 바뀌지 않음.

- 팀 액션: default launch path 대비 p50/p95 build time·failure rate·AMI hash·ASG capacity pressure 비교

- 시사점: 시사점: ASG pool을 build 전용 account 또는 subnet에 격리하고, base AMI·patch level·instance profile·component version·artifact hash·cleanup 결과를 build manifest에 남길 것. 기존 launch path와 ASG path의 build duration, failure rate, image drift, capacity pressure를 canary로 비교할 것.

### 4. Google 연구팀, open-world agent용 재귀 self-improvement 프레임워크 `Harness²` 공개

- 출처: [AI타임스](https://www.aitimes.com/news/articleView.html?idxno=216410)

핵심: Google Research가 공개한 `Harness²`는 ground-truth verifier가 없는 open-world task에서 agent harness를 task-level과 harnessing-level의 두 단계 재귀로 개선하는 연구 프레임워크임. arXiv는 GLM-5·Gemini 3.5 Flash의 base harness 대비 WorkBuddy-Bench 최대 **11.5점**, JobBench 4.5점, LAB 11.8 percentage point 개선을 보고했으나, 세 professional benchmark와 네 model-harness configuration의 연구 결과이므로 production agent의 일반 성능·안전성·비용 개선을 보장하지 않음.

`Harness²`는 task-level recursion에서 ground-truth verifier 없이 contrastive Propose-Probe-Compose 절차로 현재 task의 harness edit를 유도하고, parallel 또는 sequential recursion으로 예산을 늘릴 수 있다고 설명함. harnessing-level recursion은 task edit 경험을 continual improvement harness에 반영해 이후 새로운 task 적응을 노림. 논문은 세 professional benchmark와 네 model-harness configuration에서 single step 개선 및 task-level recursion budget 증가에 따른 추가 향상을 보고함. 그러나 online harness edit는 prompt·tool·policy·memory·routing의 행동을 바꿀 수 있어 benchmark score와 별도로 write 권한, prompt injection, cost explosion, regression, rollback, audit trace를 release control로 검증해야 함.

Google Research가 `Harness²`를 공개했고, AI타임스는 19일 KST 관련 연구를 보도함. arXiv 원문은 LLM agent capability가 base model뿐 아니라 execution harness에 의존하며, open-world 환경의 recursive self-improvement 문제를 다룬다고 설명함.

- 구성: task-level recursion과 harnessing-level recursion을 연결한 plug-and-play framework
- 문제: 설계 때 보지 못한 task와 test-time novelty 때문에 online harness edit를 ground-truth verifier로 유도하기 어려운 조건

#### 방법과 측정 결과

task-level recursion은 contrastive `Propose-Probe-Compose` 단계로 현재 task harness를 개선하고 parallel 또는 sequential recursion 확장이 가능하다고 제시함. harnessing-level recursion은 task edit 경험을 continual improvement harness에 반영하는 구조임.

- 결과: WorkBuddy-Bench 최대 **11.5점**, JobBench 4.5점, LAB 11.8 percentage point 개선이라는 논문 보고
- 조건: 세 professional benchmark와 네 model-harness configuration, GLM-5·Gemini 3.5 Flash base harness 비교 범위

#### 평가 경계와 운영 위험

연구의 score 상승은 production tool call, external write, sensitive data, incident handling에서의 성공률·비용·안전성을 자동 증명하지 않음. verifier가 없는 환경에서 harness edit가 prompt, tool routing, memory, policy를 바꾸면 hidden regression과 권한 확대가 발생할 수 있음.

- 리스크: self-improvement edit가 prompt injection, tool misuse, cost increase, stale memory, policy bypass를 새 경로로 만들 가능성

#### 시사점

self-improving agent의 control plane은 model output보다 change evidence가 중요함. candidate edit를 sandbox·read-only task에서 probe하고, holdout evaluation과 human approval을 거쳐 canary로 배포하며, metric regression 또는 policy violation 때 이전 harness로 돌아갈 수 있어야 함.
