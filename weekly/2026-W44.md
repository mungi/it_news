## Deep Dive

### AWS Continuum GA: context graph·sandbox proof를 remediation PR 통제로 연결하는 방법

한 줄 결론: AWS Continuum은 code finding을 AWS resource·identity·network context와 isolated sandbox exploitability 검증에 결합해 remediation PR로 연결함. value는 자동 patch 수가 아니라 graph freshness, sandbox fidelity, CI·approval·rollback evidence를 가진 좁은 Enforce mode 운영에 있음.

- 일일 재검토: 2026-10-24 00:07 KST

#### 한 줄 결론

AWS Continuum은 code finding을 AWS resource topology·identity relationship·network reachability의 context graph와 결합하고 isolated sandbox에서 exploitability를 시험해 remediation PR로 연결하는 GA 서비스임. 자동 수정 확대 여부는 finding 수가 아니라 graph freshness, sandbox fidelity, PR 검증과 write authority 증거로 결정할 대상임.

- 변화: scanner finding을 환경 attack path·business impact·blast radius 근거와 함께 우선순위화하는 범위
- 결정: Enforce mode 전환은 exploit proof 재현성·CI test·human override·rollback evidence가 갖춰진 repository에 한정

#### 원문과 관련 뉴스의 핵심 내용

AWS 공지는 Continuum이 vulnerability finding 수집과 source code scan을 결합하고, AWS 환경의 topology·identity·network reachability로 context graph를 구성한다고 설명함. isolated sandbox validation 뒤 exploitability proof와 blast radius assessment를 첨부한 remediation pull request를 제공하며 GuardDuty·Security Hub와 연계하는 범위임.

- 원문 사실: discovery·validation·prioritization·remediation workflow를 하나의 서비스 범위로 제시
- 원문 사실: Learn mode에서 수정안을 검토하고 guardrail 안에서 Enforce mode로 이동하는 운영 모델

#### AI·Infra 전문가 해석

CVSS 또는 code scan 결과만으로는 workload가 internet-reachable인지, role이 lateral movement를 허용하는지, asset이 business critical인지가 빠질 수 있음. context graph는 triage 근거를 보강하지만 IAM·network·asset inventory가 늦거나 틀리면 priority 자체가 왜곡될 수 있음. sandbox exploitability도 production data, secret, dependency, egress 조건을 그대로 재현한다는 뜻은 아님.

- 볼 것: graph input의 수집 시각·coverage·unknown edge와 sandbox fixture·network·IAM parity
- 피할 것: proof가 붙은 finding을 production exploit 또는 patch correctness 확정으로 해석하는 운영

#### 아키텍처·운영 관점

도입은 scanner를 교체하는 일이 아니라 finding ingest, context graph, sandbox, PR, CI, approval, deploy, rollback을 연결하는 control plane 설계임. sandbox와 production은 분리하되 evidence schema와 correlation ID는 이어져야 함. PR 생성과 merge·deployment 권한은 동일 principal에 몰지 않는 separation of duties가 필요.

- 설계: finding ID·graph snapshot·sandbox run·PR·test·approval·deploy·rollback을 하나의 audit chain으로 연결
- 검증: graph stale 상태·sandbox failure·CI failure·PR conflict·emergency disable을 포함한 negative path rehearsal

#### 보안·거버넌스 관점

source code, finding evidence, resource relationship, identity information이 서비스 처리 경로에 들어갈 수 있으므로 data classification과 access scope를 먼저 결정해야 함. Enforce mode가 branch 또는 infrastructure write를 만들 수 있다면 repository protection, CI secret masking, change approval, CloudTrail과 SCM audit 보존을 기존 정책에 연결해야 함.

- 통제: service role의 read/write scope를 account·repository·branch·environment별로 축소
- 통제: remediation author, PR approver, deploy approver, emergency-disable actor를 역할로 분리

#### SRE·FinOps 관점

자동 triage는 analyst 시간을 줄일 가능성이 있으나 sandbox 실행, graph ingestion, PR 재시도, CI fan-out이 새 비용과 queue를 만들 수 있음. 원문은 precision·coverage·MTTR·비용 절감 수치를 보장하지 않으므로 canary에서 accepted PR rate, false positive, missed exposure, rollback time, finding-to-fix lead time을 baseline과 비교해야 함.

- 측정: finding당 sandbox run·PR 생성·CI minute·human review·rollback과 완료 remediation cost
- 결정: high-risk asset의 false negative와 low-risk asset의 noisy PR에 서로 다른 error budget 설정

#### 도입 로드맵

첫 단계는 non-production account와 고정된 repository 한 곳에서 Learn mode를 운영하고, asset graph와 sandbox 조건을 사람이 대조하는 것임. 다음 단계에서 low-risk dependency 또는 configuration fix만 PR canary로 확대하고, Enforce mode는 write scope·test gate·rollback·emergency disable을 검증한 뒤 제한적으로 적용해야 함.

- 1단계: representative finding 20~50건에 graph evidence·sandbox reproducibility·owner mapping 수집
- 2단계: human-approved PR canary에서 test pass·review latency·false positive·rollback 시간 비교
- 3단계: guardrail-bound Enforce mode를 narrow branch·environment에 적용하고 audit export 상시 점검

#### 개발팀·인프라팀 체크리스트

개발팀은 test fixture와 PR acceptance를, cloud platform 팀은 graph와 IAM·network inventory를, security 팀은 finding policy와 exception을, SRE는 deploy·rollback SLO를 소유해야 함. service의 recommendation과 production change approval을 같은 화면의 자동 승인으로 묶지 않는 책임 분리가 필요.

- 체크: exploit proof가 동일 dependency·configuration·network 조건에서 재현되는지 확인
- 체크: PR이 secret·production credential·protected branch·deployment role에 접근하지 않는지 policy test
- 체크: emergency disable 뒤 finding queue·manual remediation·audit retrieval이 계속 가능한지 drill

#### 강조 메세지

AWS Continuum의 가치는 취약점 개수를 더 많이 처리한다는 주장보다, 실제 exposure 가능성이 높은 finding에 검증 근거와 수정 workflow를 연결하는 데 있음. 이번 주에는 자동 merge가 아니라 Learn mode의 evidence 품질과 rollback 가능한 PR 경로를 먼저 계측할 대상임.

- 발표 포인트: context graph·isolated sandbox·exploitability proof·blast radius PR·Learn→Enforce 경계
- 즉시 행동: 고위험 repository 한 곳에서 finding→proof→PR→CI→approval→rollback trace를 수집

### Kamaji·HAMi GPU 멀티테넌시: tenant control plane과 fractional GPU admission을 검증하는 순서

한 줄 결론: Kamaji·HAMi lab은 tenant별 Kubernetes API 분리와 GPU memory·compute slice scheduling을 한 management cluster에서 연결함. mock device로 확인한 것은 control-plane·admission wiring이며, production 승인은 real GPU isolation·latency·noisy-neighbor·failure recovery 측정값으로 결정해야 함.

- 일일 재검토: 2026-10-24 00:07 KST

#### 한 줄 결론

Kamaji와 HAMi 조합은 tenant별 Kubernetes control plane 격리와 GPU memory·compute fraction scheduling을 함께 실험할 수 있는 패턴임. 다만 단일 Linux host의 mock GPU lab은 control-plane wiring과 admission decision을 검증한 것이며, real GPU isolation·throughput·noisy-neighbor·production support를 증명하지 않음.

- 변화: control plane per team 비용과 shared cluster의 약한 격리 사이에서 tenant API separation과 fractional GPU를 결합
- 결정: 실환경 채택 전에는 Konnectivity·webhook·device plugin failure domain과 GPU QoS evidence를 별도로 확보

#### 원문과 관련 뉴스의 핵심 내용

CNCF 게시글은 one kind management cluster 위에 Kamaji tenant control plane 두 개와 tenant별 worker를 구성하고 HAMi mock device plugin으로 GPU capacity를 선언하는 lab을 공개함. tenant-a A100 80GB mock과 tenant-b L4 mock을 사용했으며, tenant-a에서는 20,000MB·30% 요청 pod 3개가 같은 card에 배치되고 과도한 90,000MB 요청은 Pending으로 남는 결과를 제시함.

- 원문 사실: API server는 management cluster에 있고 HAMi webhook은 tenant worker에 있어 Konnectivity tunnel이 admission 경로가 됨
- 원문 사실: mock plugin의 node lock은 실제 device plugin과 달리 수동 해제가 필요한 lab-only artifact

#### AI·Infra 전문가 해석

multi-tenancy에는 API/etcd/RBAC 격리와 accelerator packing이 동시에 필요하지만 동일한 문제는 아님. Kamaji는 control plane density를, HAMi는 GPU allocation policy를 다룸. 두 계층을 붙이면 admission path가 길어지고 webhook·tunnel·scheduler의 dependency chain이 늘어남. tenant isolation claim은 Kubernetes object visibility만으로 끝나지 않고 node, CNI, image registry, secret, GPU driver, observability plane까지 확장돼야 함.

- 볼 것: tenant별 control-plane SLO, webhook latency, scheduler queue, node-level GPU contention, management cluster blast radius
- 피할 것: mock scheduler success를 production CUDA performance 또는 memory isolation 검증으로 대체하는 판단

#### 아키텍처·운영 관점

management cluster는 Kamaji control plane과 shared etcd를, tenant worker는 각 tenant API와 CNI·HAMi components를 보유하는 구조임. API server가 tenant worker webhook까지 도달하지 못하면 GPU pod가 normal scheduler로 fallback하거나 admission 자체가 실패할 수 있음. 운영 설계에는 tunnel health, webhook certificate, API reachability, version skew, node join·drain·upgrade 절차를 넣어야 함.

- 검증: Konnectivity RTT·webhook timeout·admission reject·scheduler queue·node lock을 tenant label로 분리 계측
- 복구: management cluster 또는 etcd degradation에서 tenant control-plane read/write와 in-flight GPU pod behavior rehearsal

#### 보안·거버넌스 관점

tenant별 kubeconfig와 API server 분리는 시작점일 뿐임. management operator가 tenant secret·audit·etcd data에 접근할 수 있는지, device plugin·NVIDIA runtime이 host 권한을 어디까지 요구하는지, registry pull credential과 network egress가 tenant별로 분리되는지를 확인해야 함. shared GPU node를 실사용한다면 device memory remanence·driver CVE·container escape 대응도 별도 threat model 대상.

- 통제: tenant RBAC·service account·kubeconfig lifecycle·audit retention을 management-plane role과 분리
- 통제: GPU operator·device plugin·node privileged daemonset의 image provenance·host access·patch window 검증

#### SRE·FinOps 관점

fractional scheduling은 빈 GPU memory와 compute slice를 활용할 수 있으나 request가 실제 usage와 다르면 overcommit·queue·tail latency가 생김. 원문 lab은 hardware가 없어 throughput·interference 데이터를 제공하지 않음. 실제 비용 평가는 card utilization만 아니라 tenant별 pending time, allocated-versus-used memory, SM utilization, job completion time, retry, support cost를 함께 봐야 함.

- 측정: namespace·tenant별 GPU request·allocation·actual utilization·queue wait·OOM·p95 job duration·cost attribution
- 결정: low-latency inference와 batch training에 동일 fractional policy를 적용하지 않고 priority·quota·preemption을 분리

#### 도입 로드맵

첫 단계는 mock lab으로 manifest, tenant onboarding, admission trace, failure injection을 검증하는 것임. 다음 단계에서 GPU 한 장과 비민감 batch workload를 대상으로 device plugin·driver·monitoring·quota·noisy-neighbor canary를 수행함. production 확대는 workload class별 SLO와 tenant isolation evidence, node failure와 upgrade rollback runbook이 확보된 뒤에만 고려할 대상.

- 1단계: no-GPU CI lab에서 tenant API reachability·HAMi admission·quota reject test 자동화
- 2단계: real node canary에서 memory·compute request, actual utilization, latency, node failure·drain behavior 비교
- 3단계: tenant별 quota·chargeback·priority·incident ownership을 계약과 dashboard로 고정

#### 개발팀·인프라팀 체크리스트

application 팀은 job profile과 latency tolerance를, platform 팀은 tenant lifecycle·network·control plane을, GPU 운영팀은 driver·device plugin·capacity·patch를, security 팀은 privileged component와 tenant boundary를 담당해야 함. shared platform의 비용 효율만으로 tenant workload를 같은 node에 합치지 않도록 workload classification이 필요.

- 체크: tenant별 API server·worker·CNI·webhook certificate·Konnectivity health와 alert ownership 확인
- 체크: GPU request와 real utilization, overcommit policy, pending timeout, preemption·eviction behavior 검증
- 체크: privileged daemonset·host device access·registry credential·audit log의 tenant data boundary 검토

#### 강조 메세지

이 사례가 제공하는 직접 증거는 tenant control plane과 fractional GPU scheduler를 한 lab에서 연결하는 방법임. production GPU platform의 승인 근거는 mock success가 아니라 real driver·workload·failure에서 얻은 isolation, latency, utilization, recovery 측정값이어야 함.

- 발표 포인트: Kamaji control plane pod, HAMi MB/% GPU request, Konnectivity admission path, mock-only lock artifact
- 즉시 행동: GPU node 한 대에서 tenant별 admission latency·queue·actual utilization·node failure drill을 포함한 2주 canary 설계

### 1. AWS Bedrock Web Search, 도메인 allow/block 목록·사용자 위치 제어 추가

- 발행: 2026-10-24 06:04 KST
- 분류: AI | 태그: AI, AWS, Bedrock, Web Search, Agent, Governance
- 출처: [AWS What’s New](https://aws.amazon.com/about-aws/whats-new/2026/10/bedrock-web-search-domain-user-location/)

핵심: AWS Bedrock Web Search가 기존 OpenAI Responses API 요청의 `web_search` tool에 도메인 필터와 사용자 위치 파라미터를 추가함. 변화: 신뢰 도메인만 grounding에 허용하거나 제외 목록을 적용하고, 지역 의존 질의의 검색 결과를 location 값으로 조정할 수 있는 범위임.

AWS는 `filters`에서 최대 100개의 `allowed_domains` 또는 최대 100개의 `blocked_domains`를 지정할 수 있다고 공지함. 사용자 위치는 지역 서비스·가용성처럼 geography가 결과에 영향을 주는 질의에 선택적으로 전달함. 제공 범위는 Web Search 지원 4개 리전이며, domain filtering은 인용 정확도·프롬프트 주입 방어·데이터 보관·write action 안전성을 보장하지 않음.

#### 무슨 일이 있었나

AWS Bedrock Web Search가 응답을 grounding하는 검색 결과의 범위를 요청 단위로 제어하는 domain filtering과 user location을 추가함. 두 값은 기존 OpenAI Responses API 요청의 `web_search` tool에서 설정하는 범위이며 별도 API surface 공개로 읽을 근거는 없음.

- 공개: `filters`로 신뢰할 도메인 또는 제외할 도메인을 검색 결과 admission에 적용하는 범위
- 공개: regional availability·local services처럼 지리 조건이 있는 질의에 optional location을 전달하는 범위

#### 본문 핵심 포인트

공지는 허용 목록과 차단 목록을 각각 최대 100개 도메인으로 지정할 수 있다고 설명함. allowed 목록은 특정 사이트만 grounding 대상으로 제한하고, blocked 목록은 원하지 않는 사이트를 제외하는 용도임. 현재 기능은 US East (N. Virginia), US East (Ohio), US West (Oregon), AWS GovCloud (US-West)의 Web Search 지원 범위에 제공됨.

- 제한: 한 요청에서 `allowed_domains` 또는 `blocked_domains`에 최대 100개 도메인 지정 범위
- 제공: 공지에 명시된 4개 Web Search 지원 AWS Region 범위

#### 왜 중요한가

agent가 웹 결과를 근거로 답변·분류·다음 행동을 결정할 때 retrieval scope가 넓으면 규정 외 출처와 지역 부적합 정보가 같은 context에 들어갈 수 있음. 도메인 제어는 source admission을 줄이는 도구이나, 신뢰 도메인 내부의 부정확한 내용·prompt injection·stale 문서까지 판정하거나 차단한다는 근거는 아님.

- 영향: 업무별 citation provenance와 허용 source policy를 요청 config에 연결할 수 있는 지점
- 경계: domain filtering만으로 answer accuracy·prompt-injection 차단·data residency 충족을 확정할 수 없는 조건

#### 시사점

초기 적용은 write 권한 없는 research 또는 support retrieval에서 시작하고, allowlist hit rate·blocked-domain fallback·citation 분포·응답 품질·region별 data path를 함께 계측해야 함. location 값은 사용자 실시간 좌표를 무조건 전달하는 설정으로 간주하지 말고, 어떤 granularity와 retention이 제품 문서·privacy policy에 허용되는지 확인한 뒤 최소값만 전달할 대상.

- 팀 액션: product별 trusted domain owner·검토 주기·emergency block 절차를 configuration repository로 관리
- 팀 액션: location on/off와 allow/block policy별 quality·citation·fallback·latency canary를 분리 측정

- 시사점: 업무별 trusted-domain manifest와 국가·리전별 location policy를 versioned configuration으로 관리하고, citation domain·block hit·fallback·grounding failure를 trace에 남긴 뒤 read-only canary에서 품질과 bypass를 검증할 필요.

### 38. CNCF, AI workload가 Kubernetes autoscaling에 요구하는 reservation·topology·DRA 관점 정리
