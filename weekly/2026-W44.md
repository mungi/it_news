### Aurora·RDS Capacity Reservations: DB 복구·확장을 capacity 확보와 비용 통제로 운영하는 방법

한 줄 결론: Aurora·RDS On-Demand Capacity Reservations는 DB instance가 필요한 순간의 AZ별 compute capacity를 확보하는 control임. migration·restore·Multi-AZ 전환의 성공 여부는 reservation만이 아니라 backup, quota, DNS, application connection, 비용 종료 조건을 포함한 rehearsal로 확인해야 함.

- 일일 재검토: 2026-10-22 03:12 KST

#### 한 줄 결론

On-Demand Capacity Reservations는 Aurora·RDS의 DB instance class·engine·Availability Zone별 compute capacity를 확보하는 기능임. DR이나 확장 준비에서 instance 생성 가능성은 높일 수 있으나, 서비스 복구를 증명하는 data-plane 결과는 별도임.

- 변화: create·restore·scale-compute·start에서 reservation reference로 확보 capacity 사용
- 결정: reservation을 DR readiness 신호가 아닌 restore rehearsal의 전제 조건으로 취급

#### 원문과 관련 뉴스의 핵심 내용

AWS는 하나 이상의 AZ에서 필요한 기간 동안 Aurora·RDS DB instance capacity를 예약할 수 있다고 공지함. Multi-AZ deployment에는 두 개 이상 AZ에 reservation을 배치할 수 있으며 모든 commercial Region이 제공 범위임.

- 원문 사실: DB instance class·engine·AZ·AZ별 reserved capacity를 선택하는 구성
- 원문 사실: immediate reservation은 언제든 취소 가능, scheduled start는 5~120일 전 설정과 minimum commitment 조건

#### AI·Infra 전문가 해석

DB capacity 부족은 restore·scale 작업 자체가 시작되지 못하는 failure mode임. 그렇지만 reservation은 snapshot 복구 시간, schema migration, connection pool 재수립, DNS propagation, cache warm-up을 대체하지 않음.

- 설계: capacity assurance·data restore·application acceptance를 각각 다른 gate와 evidence로 분리
- 피할 것: Multi-AZ reservation 보유만으로 cross-AZ failover와 customer recovery 완료를 선언하는 운영

#### 아키텍처·운영 관점

예약한 capacity를 쓰려면 create·restore·modify·start 작업이 적절한 reservation을 reference해야 함. instance class나 engine, AZ topology가 runbook과 달라지면 reservation이 있어도 계획한 작업과 맞지 않을 수 있음.

- 검증: production과 동등한 class·engine·parameter group·AZ 조합으로 restore canary 실행
- 운영: reservation ID·AZ·instance class·engine·start/end window를 IaC·change ticket·DR runbook에 동시 기록

#### SRE·FinOps 관점

active reservation은 내부 DB instance가 실행되지 않아도 On-Demand rate로 청구됨. 기존 Reserved DB Instances나 Database Savings Plans 할인 적용은 원문 범위이나, 조직별 effective cost와 idle cost는 별도 cost allocation으로 확인할 필요.

- 측정: reservation utilization, active-but-unused hours, restore success, capacity-related failure, recovery elapsed time
- 통제: scheduled start와 cancel 권한을 분리하고 종료 전 alert·owner·budget code를 지정

#### 보안·거버넌스 관점

capacity reservation 생성·reference·취소는 recovery posture와 비용을 바꾸는 control-plane 권한임. 긴급 restore 시 평소와 다른 AZ 또는 account에 data를 배치할 수 있으므로 IAM, encryption key, network egress, data residency를 rehearsal에 포함해야 함.

- 통제: DBA·SRE·FinOps의 reservation create/cancel 및 restore approval 권한 분리
- 통제: snapshot KMS key·secret·security group·subnet group이 target AZ 조합에서 재사용되는지 사전 점검

#### 도입 로드맵

먼저 가장 높은 RTO risk를 가진 DB 한 개에서 restore·scale baseline을 수집하고 reservation을 연결한 canary를 반복하는 순서가 안전함. 이후 Multi-AZ와 seasonal peak로 범위를 확대하되 매 예약의 종료·갱신 결정을 monthly FinOps review에 묶어야 함.

- 1단계: DB class·engine·AZ·quota·backup·restore time inventory와 capacity-failure history 수집
- 2단계: reservation reference를 포함한 restore·scale·cancel drill, 실제 recovery acceptance 확인
- 3단계: Multi-AZ·peak plan 확대와 idle cost threshold·expiry cleanup 자동화

#### 개발팀·인프라팀 체크리스트

애플리케이션팀은 connection retry·readiness·schema compatibility를, DBA는 restore와 parameter set을, 플랫폼팀은 AZ capacity·quota·IAM을, FinOps는 active reservation cost와 종료 조건을 공동 소유해야 함.

- 체크: 대표 restore와 scale job의 reservation reference·AZ·DB class·engine evidence 확보
- 체크: failover 뒤 application health, DNS/endpoint, connection pool, queue backlog, rollback time 측정

#### 강조 메세지

이 기능은 DB instance capacity의 불확실성을 줄이는 도구이지 자동 DR 완료 장치가 아님. 이번 주에는 실제 복구 경로 하나를 선택해 capacity reservation, backup restore, application health, unused-cost alert를 하나의 drill에서 확인해야 함.

- 발표 포인트: AZ별 capacity 확보, lifecycle 작업 reference, active-but-unused 비용 조건
- 즉시 행동: 가장 중요한 DB의 restore canary와 reservation expiry·cancel ownership 등록

### PHP php2shell: WAF 완화와 origin 패치·침해 확인을 분리하는 긴급 대응

한 줄 결론: CISA는 `CVE-2026-109618`·`CVE-2026-109619` php2shell에 대해 PHP 8.5.12·8.4.27·8.3.36·8.2.35 업데이트와 internet-facing 시스템 우선 patch를 촉구함. WAF는 patch 전 임시 보호일 수 있으나 unsupported PHP 8.1 이하와 direct origin·container image·worker process를 포함한 runtime evidence 없이는 closure가 아님.

- 일일 재검토: 2026-10-22 03:12 KST

#### 한 줄 결론

CISA는 php2shell `CVE-2026-109618`·`CVE-2026-109619`이 web request를 처리하는 PHP installation에 영향을 줄 수 있는 unauthenticated RCE라고 공지하고 즉시 patch를 권고함. 패치와 exposure closure는 version, process restart, internet path, hunting evidence를 함께 확인해야 함.

- 변화: PHP 8.5.12·8.4.27·8.3.36·8.2.35 fixed release 명시
- 팀 액션: internet-facing PHP asset inventory와 fixed-runtime redeploy를 최우선 incident workstream으로 지정

#### 원문과 관련 뉴스의 핵심 내용

CISA는 공개 시점에 해당 취약점의 exploitation을 관측하지 않았다고 밝혔으나, 미패치 상태가 조직에 risk를 준다고 평가함. 즉시 업데이트할 수 없거나 unsupported PHP 8.1 이하를 운용하면 patch 또는 update 전 PHP system을 offline으로 전환하도록 권고함.

- 원문 사실: WAF는 update 또는 patch 전 일부 protection을 제공할 수 있는 임시 수단
- 원문 사실: PHP worker process의 shell launch 또는 tool download 같은 suspicious activity 모니터링 권고

#### AI·Infra 전문가 해석

긴급 web-runtime 대응의 실패 지점은 package version만 확인하고 실제 serving process와 image digest를 확인하지 않는 데 있음. reverse proxy·CDN 뒤에 있어도 direct origin, staging, admin path, queue worker, old container replica가 남을 수 있음.

- 설계: asset→image→runtime→listener→WAF policy→restart evidence를 하나의 closure graph로 추적
- 피할 것: WAF block count 감소를 patch completion 또는 compromise absence로 해석하는 운영

#### 아키텍처·운영 관점

PHP는 standalone runtime뿐 아니라 CMS, framework, appliance, container base image와 managed host dependency에 embedded될 수 있음. 따라서 repository dependency search만으로 inventory를 끝내지 말고 process list, package manager, SBOM, deployment manifest, ingress path를 대조해야 함.

- 검증: production·staging·DR·batch worker별 PHP version, process start time, image digest, external listener 수집
- 검증: CDN/WAF bypass 가능 origin endpoint, load balancer health path, admin/maintenance endpoint 분리 점검

#### 보안·침해 대응 관점

패치 전후에 web request log, WAF event, PHP-FPM·web server error log, EDR process tree, outbound DNS·HTTP를 보존해야 incident triage가 가능함. shell 실행이나 tool download의 CISA 예시는 hunting priority이며, 발견 시 secret rotation·scope assessment를 병렬로 시작할 필요.

- 통제: public ingress rule·WAF rule 변경과 origin patch/change ID를 동일 incident ticket에 연결
- 통제: suspicious child process·temporary directory write·egress event를 fixed version deployment 이후에도 재검토

#### SRE·FinOps 관점

긴급 patch는 rolling deploy·cache clear·restart로 latency와 error rate를 변화시킬 수 있음. unsupported version의 temporary offline 전환은 availability cost가 있으나 RCE exposure의 residual risk와 비교해 승인해야 함.

- 측정: fixed-version coverage, restart completion, 5xx/latency, WAF match, direct-origin request, suspicious process count
- 결정: maintenance window 예외·offline 여부·rollback 기준을 service owner와 security incident commander가 공동 승인

#### 도입 로드맵

먼저 external exposure가 있는 asset에서 version·runtime·restart 증거를 확보하고, 다음으로 internal service와 CI image를 sweep하는 순서가 필요. 이후 WAF와 logging을 보조 control로 정리하고, unsupported PHP의 retirement 계획을 deadline과 owner로 관리해야 함.

- 1단계: internet-facing PHP asset·version·owner·ingress inventory와 WAF coverage 확인
- 2단계: fixed release image build·deploy·restart, health·synthetic test, origin bypass test 실행
- 3단계: hunt 결과·secret rotation·unsupported runtime decommission·post-incident review 완료

#### 개발팀·인프라팀 체크리스트

개발팀은 framework/CMS compatibility와 regression test를, 플랫폼팀은 build artifact·deployment·ingress를, 보안팀은 WAF·hunting·incident evidence를 담당해야 함. patch 성공과 operational closure를 한 owner에게 넘기지 않는 분리가 필요.

- 체크: PHP 8.5.12·8.4.27·8.3.36·8.2.35 적용 대상과 unsupported 8.1 이하 system disposition 확인
- 체크: runtime process version·image digest·restart timestamp·external scan·suspicious activity review를 closure evidence로 첨부

#### 강조 메세지

php2shell 대응의 완료 기준은 WAF enabled가 아니라 모든 exposed PHP runtime이 fixed version으로 재배포되고, direct origin을 포함한 ingress와 compromise signal을 확인한 상태임. 지금은 version inventory와 runtime restart evidence를 먼저 고정해야 함.

- 발표 포인트: CISA fixed release, unsupported version offline 권고, WAF의 임시 보호 경계
- 즉시 행동: external PHP asset부터 patch·redeploy·restart·hunt를 같은 incident workflow로 실행

### 21. Google 연구팀, open-world agent용 재귀 self-improvement 프레임워크 `Harness²` 공개

- 발행: 2026-10-19 18:01 KST
- 분류: AI | 태그: Google Research, AI Agent, Agent Harness, Recursive Self-Improvement, Benchmark, AI Safety, Evaluation
- 출처: [AI타임스](https://www.aitimes.com/news/articleView.html?idxno=216410)

핵심: Google Research가 공개한 `Harness²`는 ground-truth verifier가 없는 open-world task에서 agent harness를 task-level과 harnessing-level의 두 단계 재귀로 개선하는 연구 프레임워크임. arXiv는 GLM-5·Gemini 3.5 Flash의 base harness 대비 WorkBuddy-Bench 최대 **11.5점**, JobBench 4.5점, LAB 11.8 percentage point 개선을 보고했으나, 세 professional benchmark와 네 model-harness configuration의 연구 결과이므로 production agent의 일반 성능·안전성·비용 개선을 보장하지 않음.

`Harness²`는 task-level recursion에서 ground-truth verifier 없이 contrastive Propose-Probe-Compose 절차로 현재 task의 harness edit를 유도하고, parallel 또는 sequential recursion으로 예산을 늘릴 수 있다고 설명함. harnessing-level recursion은 task edit 경험을 continual improvement harness에 반영해 이후 새로운 task 적응을 노림. 논문은 세 professional benchmark와 네 model-harness configuration에서 single step 개선 및 task-level recursion budget 증가에 따른 추가 향상을 보고함. 그러나 online harness edit는 prompt·tool·policy·memory·routing의 행동을 바꿀 수 있어 benchmark score와 별도로 write 권한, prompt injection, cost explosion, regression, rollback, audit trace를 release control로 검증해야 함.

#### 무슨 일이 있었나

Google Research가 `Harness²`를 공개했고, AI타임스는 19일 KST 관련 연구를 보도함. arXiv 원문은 LLM agent capability가 base model뿐 아니라 execution harness에 의존하며, open-world 환경의 recursive self-improvement 문제를 다룬다고 설명함.

- 구성: task-level recursion과 harnessing-level recursion을 연결한 plug-and-play framework
- 문제: 설계 때 보지 못한 task와 test-time novelty 때문에 online harness edit를 ground-truth verifier로 유도하기 어려운 조건

#### 방법과 측정 결과

task-level recursion은 contrastive `Propose-Probe-Compose` 단계로 현재 task harness를 개선하고 parallel 또는 sequential recursion 확장이 가능하다고 제시함. harnessing-level recursion은 task edit 경험을 continual improvement harness에 반영하는 구조임.

- 결과: WorkBuddy-Bench 최대 **11.5점**, JobBench 4.5점, LAB 11.8 percentage point 개선이라는 논문 보고
- 조건: 세 professional benchmark와 네 model-harness configuration, GLM-5·Gemini 3.5 Flash base harness 비교 범위

#### 평가 경계와 운영 위험

연구의 score 상승은 production tool call, external write, sensitive data, incident handling에서의 성공률·비용·안전성을 자동 증명하지 않음. verifier가 없는 환경에서 harness edit가 prompt, tool routing, memory, policy를 바꾸면 hidden regression과 권한 확대가 발생할 수 있음.

- 경계: benchmark 개선을 모델 일반 우위나 autonomous production deployment 근거로 확대하지 않을 것
- 리스크: self-improvement edit가 prompt injection, tool misuse, cost increase, stale memory, policy bypass를 새 경로로 만들 가능성

#### 시사점

self-improving agent의 control plane은 model output보다 change evidence가 중요함. candidate edit를 sandbox·read-only task에서 probe하고, holdout evaluation과 human approval을 거쳐 canary로 배포하며, metric regression 또는 policy violation 때 이전 harness로 돌아갈 수 있어야 함.

- 팀 액션: harness diff·task context·probe evidence·model/tool version·IAM scope·cost·approval·rollback을 trace로 보존
- 팀 액션: frozen baseline과 holdout task로 quality·latency·tool cost·policy violation을 함께 비교
- 팀 액션: external write는 idempotency·approval·compensation path가 있는 canary 뒤에만 적용

- 시사점: 시사점: harness self-improvement는 read-only·sandbox task에서 시작하고, edit diff·task context·probe outcome·tool/IAM scope·cost·safety policy decision·human approval·rollback 결과를 append-only trace로 보존해야 함. holdout task와 frozen baseline 없이 online edit를 production write path에 연결하지 말 것.
