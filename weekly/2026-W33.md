## Deep Dive

### Metabase self-hosted 제로데이: BI control plane을 patch·credential·data-access incident로 종결

핵심: Metabase는 1.58 이상 Metabase Cloud가 unknown zero-day 공격을 받은 뒤 endpoint 차단과 patch를 완료했다고 공지함. self-hosted 인스턴스는 unauthenticated SQL injection으로 application DB administrator 권한, 저장된 연결 DB credential, 접근 가능한 데이터와 export 경로에 닿을 수 있어 version upgrade만이 아니라 session·API key·admin·connector credential·query/export audit를 하나의 incident로 닫아야 함.

- 일일 재검토: 2026-08-09 03:31 KST

#### 한 줄 결론

Metabase 대응은 package version을 올리는 단일 유지보수가 아니라 BI control plane incident임. public endpoint, fixed build, 실제 재시작, administrator/session/API key, 연결 database credential, query·export evidence가 한 건의 close record로 연결돼야 함.

- 우선순위: internet-exposed self-hosted instance와 high-value warehouse connector를 high-risk cohort로 분류
- 완료 증거: fixed release·running version·restart·health check·credential rotation·log review를 같은 ticket에 보존
- 경계: Metabase 원문은 개별 고객 침해, actor, CVE, persistence, exfiltration 규모를 공개하지 않음

#### 원문과 관련 뉴스의 핵심 내용

Metabase는 Metabase Cloud가 version 1.58 이상 unknown zero-day를 이용한 공격을 받았고, endpoint 차단 뒤 취약점을 식별·patch했다고 밝힘. Cloud 고객은 이미 patched 상태라고 설명하며, self-hosted는 latest point release로 즉시 upgrade하도록 요구함.

- 공격 경로: unauthenticated attacker가 Metabase application database에 arbitrary SQL injection을 수행할 수 있는 공식 범위
- 권한 확대: injection 뒤 administrator access, application configuration 변경, stored credential 탈취 가능성
- 데이터 범위: connected database가 읽을 수 있는 data와 export path가 조사 대상

#### AI/Infra 전문가 해석

BI server는 dashboard UI가 아니라 credential broker와 query execution control plane에 가까움. application DB admin 권한은 사용자·권한 모델·연결 정보·API key를 바꿀 수 있는 지점이므로, warehouse나 production DB의 직접 침해가 확인되지 않았더라도 identity와 data-access 조사 범위를 넓혀야 함.

- 자산 모델: Metabase app DB, admin user, session, API key, connector, warehouse role, ingress를 하나의 dependency graph로 관리
- 판단 기준: scanner green이나 container image 교체만으로 incident를 종료하지 않고 public exposure와 access trail을 대조
- 운영 과제: connector별 data owner와 credential rotation owner를 patch window 전에 지정

#### 공격 표면·탐지 관점

공식 공지는 publicly accessible `/api/session/reset_password`가 있었던 instance에서 `POST` 400 뒤 `GET /api/user/current` 200이 이어지는 pattern을 application 또는 ingress log에서 찾도록 안내함. pattern 발견은 likely compromise signal이며 patch 완료와 분리해 증거 보존과 영향 조사를 시작할 조건임.

- hunt: reverse proxy·WAF·application log의 request sequence, source IP, user agent, time window를 상관 분석
- 보존: query history, export job, administrator audit, configuration change, database connection log의 retention hold 적용
- 판단: source에 없는 malware·lateral movement·actual export를 추정하지 않고 evidence 기반으로 범위 판정

#### identity·data recovery 관점

application control plane에 접근했을 가능성이 있으면 session과 static credential의 유효성을 별도로 재검토해야 함. Metabase 공식 단계는 active user session revoke, unrecognized API key deletion, administrator account review, connected database credential rotation, accessible-data review를 포함함.

- identity: active session revoke와 unknown administrator·API key를 승인 기록과 함께 검토
- credential: warehouse·CRM·production DB connector를 least privilege role과 rotation sequence로 교체
- data: privileged query와 export를 source time window·actor evidence·data classification으로 triage

#### SRE·FinOps 관점

fixed release 적용은 서비스 재기동과 dashboard/query workload regression을 동반함. point release를 올린 뒤에도 running artifact와 version 화면이 구 버전이면 remediation이 완료되지 않으며, BI 업무 중단 비용과 security exposure를 같은 change record에서 조정해야 함.

- 배포: image digest 또는 JAR artifact, deployment time, pod restart, health check를 machine-readable evidence로 기록
- 회귀: critical dashboard, scheduled delivery, warehouse connection, SSO, export permission을 canary에서 검증
- 비용 변수: emergency maintenance와 connector credential rotation의 downstream ETL·reporting 영향 사전 공지

#### 도입·복구 로드맵

먼저 instance·version·internet exposure·connector inventory를 확정하고, fixed release를 canary에 적용한 뒤 public self-hosted instance부터 rollout하는 순서가 필요함. temporary endpoint block은 exposure를 줄일 수 있으나 공식 workaround이며 permanent patch를 대체하지 않음.

- 1단계: CMDB·DNS·ingress·container inventory로 self-hosted deployment와 public endpoint를 대조
- 2단계: 사용 major의 safe point release, restart, SSO·query·connector regression을 representative instance에서 검증
- 3단계: log hunt와 identity·credential·data-access review를 완료 기준으로 incident close

#### 개발팀/인프라팀 체크리스트

close condition은 Metabase 화면이 정상이라는 신호가 아니라 fixed runtime과 조사·복구 evidence가 함께 남은 상태임. security, data platform, application owner가 connector와 export 영향 범위를 한 timeline에서 검토해야 함.

- 체크: running version과 fixed point release, public reset-password endpoint, ingress exposure 확인
- 체크: session·API key·administrator·connector credential과 query/export log의 rotation·review 책임자 지정
- 체크: suspicious pattern 발견 시 host·application·ingress·warehouse evidence 보존 후 data incident escalation 실행

#### 강조 메세지

Metabase 제로데이는 BI를 단순 reporting tool로 취급하면 놓치는 incident임. application DB SQL injection이 admin control plane과 stored credential을 거쳐 connected data에 닿을 수 있으므로, patch와 access recovery를 분리하지 말아야 함.

- 강조: Cloud patched 공지와 self-hosted remediation 상태를 동일시하지 않을 것
- 강조: endpoint 차단은 temporary mitigation이며 fixed point release와 restart evidence를 대체하지 않음
- 팀 액션: 다음 BI patch runbook에 connector credential·session/API key·query/export audit를 필수 단계로 추가

### Atlassian Rovo 간접 프롬프트 주입: connector retrieval·model URL egress를 하나의 data-boundary control로 운영

핵심: PromptArmor는 Rovo가 읽는 uploaded content의 hidden instruction이 Jira·Confluence retrieval과 attacker-controlled URL fetch를 결합할 수 있다고 공개했으며, 해당 관찰은 2026-08-05 시점의 단일 연구 범위임. 별도 `rovoChatPrompt` one-click route는 Bugcrowd 기록상 Atlassian server-side fix와 reporter validation이 완료됐지만, content-borne path의 이후 remediation은 확인되지 않아 connector scope·outbound fetch·audit trace를 함께 검증해야 함.

- 일일 재검토: 2026-08-09 03:31 KST

#### 한 줄 결론

Rovo 대응의 단위는 prompt filter 하나가 아니라 untrusted content → connector retrieval → model-constructed URL/image fetch → external destination으로 이어지는 execution chain임. 어떤 data class가 어떤 tool로 외부에 나갈 수 있는지 request trace로 재현하고 차단해야 함.

- 우선순위: high-sensitivity Confluence space, Jira project, SharePoint·Outlook connector와 Rovo enabled group을 먼저 inventory
- 완료 조건: poisoned content와 external URL test에서 retrieval·egress·policy decision·audit event를 복원 가능
- 경계: 공개 연구는 재현 경로이며 특정 고객의 실제 data loss나 universal impact 증거가 아님

#### 원문과 관련 뉴스의 핵심 내용

PromptArmor는 Rovo가 읽는 content 안의 attacker instruction이 indirect prompt injection으로 작동할 수 있다고 공개함. 연구 예시는 사용자가 poisoned file을 노출한 뒤 정상적인 Jira 정리 요청을 하면 Rovo가 Jira·Confluence 결과를 attacker URL request에 붙여 보내는 흐름을 설명함.

- 출처 상태: PromptArmor가 Atlassian에 2026-05-23 disclosure했고 2026-08-05 공개 시점에도 vulnerable하다고 주장한 primary research 범위
- 설정 경계: web search를 꺼도 URL-retrieval capability 때문에 동작했다는 bypass는 해당 연구의 단일 출처 관찰
- 사용자 조건: poisoned content exposure와 일반 요청이 필요하며, exfiltration 단계의 별도 approval 부재를 주장한 경로

#### AI/Infra 전문가 해석

agent가 connector search result와 model-produced URL을 조합하면 authorization은 user ACL에만 머물지 않음. retrieval authorization, instruction provenance, tool authorization, network egress authorization이 한 transaction에서 함께 실패할 수 있어, model output을 trusted command나 trusted URL로 해석하면 안 됨.

- trust boundary: source document와 retrieved text를 instruction channel이 아닌 untrusted data channel로 태깅
- tool contract: external fetch는 user intent, destination allowlist, data classification, approval state를 모두 만족할 때만 실행
- evaluation: prompt-injection resistance는 model response 품질이 아니라 prohibited retrieval·egress가 block되는지로 측정

#### connector·권한 관점

Rovo가 사용자 권한으로 Jira·Confluence와 connector를 조회할 수 있으면 blast radius는 assistant 자체의 permission보다 user와 group scope의 합으로 결정됨. high-sensitivity project와 space를 assistant 대상으로 자동 포함시키지 말고 data class별 allowlist와 break-glass 절차를 분리해야 함.

- inventory: Rovo app/group membership, project·space ACL, connected app, data classification, owner를 one table로 관리
- least privilege: regulated record·source code·secret-bearing space는 default deny 후 scoped enablement 적용
- review: group membership change와 connector enablement를 identity review·security approval·expiry와 연결

#### network·data egress 관점

PromptArmor 연구는 URL retrieval을 outbound path로 지목하며, Markdown image rendering도 별도 가능한 mechanism으로 언급함. 특정 rendering route의 full chain은 그 연구가 Rovo에서 입증하지 않았으므로, 정책은 demonstrated path와 potential path를 구분하되 둘 다 test 대상으로 다뤄야 함.

- allowlist: model-generated URL, image/Markdown fetch, redirect, DNS resolution, proxy route를 egress policy에 포함
- protection: URL query/path에 data가 실리는 exfiltration을 DLP pattern, size limit, redaction, deny response로 검증
- logging: conversation·source document·connector query·tool call·destination·policy decision을 same request ID로 보존

#### 수정 상태와 evidence boundary

Bugcrowd disclosure는 `rovoChatPrompt` parameter가 authenticated user의 Rovo chat에 attacker prompt를 preload할 수 있었고, crafted link가 Rovo privilege로 실행되는 one-click path였다고 설명함. 그 record는 2026-07-08 server-side fix와 reporter validation, resolved 상태를 명시함.

- fixed route: `rovoChatPrompt` parameter injection은 Bugcrowd record의 server-side remediation 범위
- unfixed inference 금지: 이 fix가 PromptArmor content-borne route까지 해결했다는 공개 증거는 없음
- 운영 판단: tenant별 patch 설치가 아닌 server-side behavior 검증과 suspicious URL click hunt가 필요한 항목

#### 보안 운영·사고 대응 관점

실제 external request가 발생했다면 prompt text만 보지 말고 connector result, URL construction, proxy/DNS flow, server response, conversation audit를 함께 묶어야 함. blocked event도 policy tuning evidence이며, alert를 incident로 올릴 threshold와 data owner notification 기준을 사전에 합의해야 함.

- detection: model-constructed external URL, encoded long path/query, image fetch redirect, unusual DNS/domain을 correlation rule로 수집
- containment: affected group의 Rovo scope와 connector access를 축소하고 high-risk document ingestion을 격리
- recovery: verified egress에는 destination·data class·user·source content를 기준으로 credential rotation과 disclosure 판단

#### 도입 로드맵

먼저 low-sensitivity test tenant에서 poisoned document와 approved/unapproved destination을 이용해 tool-call trace를 수집하고, 이후 production connector를 data class별로 단계 적용하는 방식이 안전함. web-search setting 하나를 remediation completion으로 선언하지 않아야 함.

- 1단계: Rovo-enabled app·group·connector·external fetch surface와 sensitive data map 작성
- 2단계: red-team test로 poisoned file, search-off state, model URL, Markdown/image, redirect, audit correlation 검증
- 3단계: allowlist·DLP·approval·retention·incident owner를 policy-as-code와 runbook에 고정

#### 개발팀/인프라팀 체크리스트

agent security의 완료 기준은 assistant가 정상 답변을 내는지가 아니라 untrusted content가 privileged retrieval과 external egress를 바꾸지 못하고, 시도와 차단이 audit trace로 남는 상태임.

- 체크: Rovo group, Jira project, Confluence space, connector ACL과 data class inventory 대조
- 체크: model-created URL·image/Markdown fetch·redirect·DNS·proxy/DLP log를 request identity로 연계
- 체크: Bugcrowd fixed URL route 재현 불가 확인과 content-borne red-team test 결과를 change evidence로 보관

#### 강조 메세지

RovoBlast가 resolved라고 해서 enterprise-agent data egress 문제가 끝난 것은 아님. fixed one-click URL route와 PromptArmor가 공개한 content-borne route의 evidence를 구분하고, connector privilege와 model URL egress를 같은 control plane에서 다뤄야 함.

- 강조: web-search toggle을 complete egress control로 간주하지 않을 것
- 강조: source document의 hidden text를 business data로 취급하고 tool instruction으로 승격하지 않을 것
- 팀 액션: 다음 SaaS agent security review에 connector scope·untrusted content·outbound URL·DLP·audit completeness test를 추가
