## Deep Dive

### MCP 2026-07-28 stateless core: session 제거 뒤 gateway·OAuth·MRTR·tool transaction을 운영 설계로 재배치

핵심: Cloudflare가 최신 MCP 2026-07-28 specification의 stateless core, required handshake·`Mcp-Session-Id` 제거, `Mcp-Method`/`Mcp-Name` HTTP header, MRTR elicitation, OAuth issuer·resource audience 변경을 설명함. request-scoped deployment는 단순해지지만 write tool·approval·task state·retry idempotency·authorization audit는 application control plane에서 더 명시적으로 운영해야 함.

- 일일 재검토: 2026-08-07 02:10 KST

#### 한 줄 결론

MCP 2026-07-28의 stateless core는 MCP server를 request-scoped infrastructure에 올릴 수 있게 하지만, session 제거가 tool authorization·resource audience·idempotency·long-running task의 운영 책임을 없애지는 않음.

- MCP server의 scale-out 판단은 sticky session 제거 여부가 아니라 request identity·authorization·tool-side effect를 request마다 검증하는지로 결정
- migration gate: protocol/version negotiation·header-aware gateway·OAuth audience·retry idempotency·observability를 같은 canary에서 확인
- 운영 지표: reconnect failure·401/403·tool error·MRTR completion·duplicate write·p95 latency·per-request cost를 이전 transport와 비교

#### 원문과 관련 뉴스의 핵심 내용

Cloudflare는 2026-08-06 `The next generation of MCP`에서 MCP 2026-07-28 specification과 TypeScript·Python·Go·C# SDK update를 설명함. Cloudflare 설명 범위에서 core protocol은 fully stateless이며 required handshake·`Mcp-Session-Id`·protocol session이 request path에서 제거됨.

- 변화: 각 request가 protocol version·client identity·client capabilities를 포함하고 `server/discover`는 optional 호출
- HTTP: Streamable HTTP request에 `Mcp-Method`·`Mcp-Name` header를 요구해 gateway가 JSON body parse 전 request type을 식별 가능
- 경계: Cloudflare의 Worker 배포 단순화·비용 감소 설명은 특정 workload의 availability·latency·cost SLA 보장이 아님

#### AI/Infra 전문가 해석: 상태·상호작용 모델

기존 remote MCP는 session state, sticky routing, open stream, replay와 deployment drain/migration을 다뤄야 했음. 새 MRTR는 server가 `input_required`를 반환하고 client가 입력을 모아 operation을 retry하는 방식으로 elicitation을 처리함.

- breaking change: open stream에 의존하던 `elicitation/create` flow는 MRTR·retry model로 migration 필요
- state boundary: protocol session이 없어도 approval state·task state·tool transaction은 application store에 명시적으로 소유·TTL·cleanup 필요
- retry boundary: approval·payment·deployment·write tool은 idempotency key·operation ID·dedup record 없이 retry하면 duplicate side effect 위험

#### gateway·observability 관점

`Mcp-Method`와 `Mcp-Name`은 gateway·WAF·rate limiter·audit pipeline이 request class를 body parse 없이 구분할 수 있는 신호임. 그러나 header 자체는 caller authorization이나 argument safety를 보증하지 않으므로 tool policy와 payload validation을 분리해야 함.

- routing: `tools/call`·`resources/read`·`prompts/list` 별 rate·timeout·egress·logging policy 분리
- audit: client ID·protocol version·method/name·resource audience·tool arguments hash·decision·result·operation ID를 trace로 결합
- security: header allowlist·canonicalization·body/header consistency·request size·replay detection을 gateway test에 포함

#### authorization·identity 관점

Cloudflare는 pre-registered client를 우선하고 CIMD를 dynamic registration에 사용하며 DCR은 신규 구현에서 deprecated·2027년 여름 이후 removal 예정이라고 설명함. RFC 9207 `iss` 비교와 RFC 8707 `resource` audience binding도 도입됨.

- client: known client에는 pre-registration, unknown client에는 CIMD, DCR 의존성은 migration inventory 대상
- issuer: authorization response의 `iss`와 사전 발견 issuer를 비교해 issuer confusion 방지
- token: canonical server URI를 resource로 요청하고 token audience·scope·tool/resource policy를 서버에서 fail-closed 검증

#### 비용·SRE 관점

stateless transport는 connection coordination을 줄일 수 있지만 MRTR retry, tool backend call, token validation, audit retention이 request cost와 tail latency를 이동시킬 수 있음. Autoscaling은 connection 수 대신 request concurrency·external dependency·write queue로 capacity를 잡아야 함.

- FinOps: request당 auth/token validation·tool backend·egress·log ingest·MRTR retry를 cost unit으로 측정
- reliability: deploy 중 in-flight request, retry storm, OAuth issuer outage, tool timeout, duplicate side effect를 chaos test
- capacity: request concurrency·tool fan-out·external API quota·audit sink backpressure를 autoscaling/queue policy에 연결

#### 도입 로드맵

새 specification을 protocol version과 feature flag로 canary 배포하고, read-only tool부터 stateless handler로 전환한 뒤 MRTR·write tool·long-running Task extension을 확대해야 함. 기존 client compatibility는 endpoint가 지원하더라도 조직별 SDK·gateway·auth deployment에서 별도 증명 필요.

- 1단계: SDK·protocol version·gateway header 전달·OAuth metadata·trace schema를 test tenant에서 고정
- 2단계: read-only tool에서 sessionless reconnect·cache hint·error/retry·token audience를 load test
- 3단계: write tool과 MRTR을 operation ID·approval record·idempotency·rollback drill을 통과한 scope에만 적용

#### 개발팀/인프라팀 체크리스트

MCP transport migration은 SDK upgrade ticket 하나가 아니라 ingress·identity·tool transaction·telemetry 변경임.

- 체크: `Mcp-Method`/`Mcp-Name` forwarding, protocol-version compatibility, body/header mismatch rejection 확인
- 체크: client registration mode·issuer discovery·`iss` validation·resource audience·scope/token TTL 확인
- 체크: MRTR timeout·retry·idempotency·approval persistence·write rollback·task cleanup drill 실행

#### 강조 메세지

MCP가 stateless가 되어도 agent가 호출하는 tool의 side effect는 stateful임. transport session을 없앤 만큼 identity, approval, transaction, audit state를 어디에 어떤 TTL과 recovery rule로 둘지 설계 문서와 운영 지표로 명확히 해야 함.

- 강조: sessionless protocol과 sessionless business operation을 동일시하지 않을 것
- 강조: HTTP header visibility는 policy enforcement의 입력이지 authorization 완료 증거가 아님
- 팀 액션: 다음 MCP migration review에 idempotency·resource audience·MRTR recovery·tool audit completeness를 release gate로 추가

### GitHub malware advisory 8개 ecosystem 확장: OSV feed를 alert가 아닌 dependency·credential incident control loop로 운영

핵심: GitHub Advisory Database가 OpenSSF malicious-packages OSV 데이터를 ingest해 npm·PyPI·Maven·RubyGems·NuGet·Go·crates.io·PHP Composer의 malware advisory와 Dependabot alert 범위를 확장함. schema validation·upstream snapshot·withdrawn·origin dedup은 feed 신뢰성 계층이며, 조직은 lockfile/SBOM·CI/endpoint execution·token·artifact evidence를 연결해야 actual exposure와 remediation을 판단 가능.

- 일일 재검토: 2026-08-07 02:10 KST

#### 한 줄 결론

GitHub의 8개 ecosystem malware advisory 확장은 dependency threat signal의 coverage를 넓히지만, 자동 alert를 신뢰할 수 있는 remediation으로 바꾸려면 feed provenance·withdrawal·package resolution·credential exposure evidence를 하나의 supply-chain control loop로 운영해야 함.

- 도입 기준: Dependabot malware alert opt-in만이 아니라 manifest·lockfile·SBOM·CI/endpoint install evidence를 연결
- 판단 기준: alert count가 아닌 mean time to validate·false-positive rollback·confirmed package removal·token rotation completeness 측정
- 운영 원칙: hostile package alert와 vulnerable version alert의 triage·evidence·remediation SLA를 구분

#### 원문과 관련 뉴스의 핵심 내용

GitHub는 2026-08-06 Advisory Database가 OpenSSF malicious-packages repository를 ingest해 npm·PyPI·Maven·RubyGems·NuGet·Go·crates.io·PHP Composer의 malware advisory와 Dependabot alert를 지원한다고 공개함. OpenSSF repository는 2023년 이후 OSV 형식 15,000건 이상 report를 축적했다는 GitHub 설명임.

- 범위: typosquat·dependency confusion·account takeover·malicious prebuilt binary 등 OSV schema가 지원하는 ecosystem data를 source로 사용
- 활성화: malware alert는 repository·organization·enterprise security settings에서 opt-in이며 enable 순간 existing advisory backfill 수행
- 경계: GitHub post는 특정 organization의 alert quality·coverage latency·package manager/runtime enforcement를 보증하지 않음

#### importer와 데이터 품질 경계

GitHub importer는 변경된 source file을 읽어 required field·type·format을 schema validation하고 실패 record는 reject·log 처리함. 유효 record는 source·identifier·CVE ID가 있으면 그 값·complete upstream snapshot·mapped publishing data로 정규화됨.

- normalize: upstream ecosystem naming·discrete affected version·missing detail·multiple report text를 GitHub data model에 맞춰 처리
- withdrawal: OpenSSF `osv/withdrawn`을 처리해 malware flag 철회 가능성을 ingestion model에 반영
- evidence: advisory record와 consumer repository의 resolved dependency·install trace는 다른 증거 층으로 유지

#### origin dedup·자동 발행 리스크

GitHub도 OpenSSF repository에 malware advisory를 기여하므로 `ghsa-malware` origin record는 import 전 drop함. GitHub는 live validation에서 새 npm report의 절반 이상이 자사 advisory의 round-trip이라 제외됐다고 설명함.

- dedup: origin metadata 없이는 동일 advisory가 feedback loop로 재수집될 위험
- speed: credential-stealing package는 시간 민감성이 높아 auto-publish path를 선택했다는 GitHub의 설명
- risk: false report·wrong package mapping·compromised source batch는 legitimate dependency를 alert 대상으로 만들 수 있는 failure mode

#### AI/Infra 전문가 해석

이 변경은 package manager별 scanner를 따로 만드는 방식보다 shared OSV feed와 single importer로 coverage를 넓히는 data-plane 결정임. 그러나 security decision은 feed ingest, repository dependency graph, build execution, credential scope, artifact provenance가 서로 다른 latency와 owner를 가진 control loop임.

- detection plane: OSV/GHSA identifier·package namespace·version·withdrawal status를 freshness SLA와 함께 저장
- exposure plane: direct/transitive dependency, lockfile resolution, cached artifact, CI runner, developer workstation install을 graph로 연결
- response plane: package remove·rebuild·token revoke·registry block·artifact quarantine를 confirmation level에 따라 분기

#### CI/CD·credential 관점

악성 package는 developer install뿐 아니라 CI dependency resolution과 build script에서 credential을 만날 수 있음. GitHub advisory가 alert를 내도 self-hosted runner·private registry mirror·artifact cache·deploy token의 노출 여부는 조직 telemetry로만 확인 가능.

- CI: workflow run·package manager command·resolved lockfile digest·runner image·network egress·secret access audit 보존
- credential: npm/PyPI/Maven registry token, VCS token, cloud role, signing key를 package incident scope에서 inventory
- containment: malicious package version block, cache purge, runner isolation, known-good rebuild, token rotation 순서와 rollback owner 정의

#### FinOps·운영 지표

8개 ecosystem으로 alert coverage가 늘면 triage volume도 늘 수 있음. 단순 alert suppression은 hostile dependency를 숨길 수 있으므로 source trust·package criticality·execution reachability·credential scope로 priority를 정해야 함.

- metrics: alert-to-validation time, confirmed/withdrawn ratio, package removal time, rebuild success, credential rotation completion
- cost: SBOM generation·dependency graph·CI log retention·artifact rebuild·runner quarantine 비용을 incident budget에 반영
- governance: auto-published advisory의 owner, exception expiry, false-positive appeal, withdrawal re-evaluation 책임을 명시

#### 도입 로드맵

먼저 repository·organization·enterprise 단위의 malware alert opt-in과 notification owner를 정하고, supported ecosystem inventory를 만든 뒤 high-privilege build path를 canary로 triage해야 함. auto-remediation은 withdrawal·namespace collision·private mirror behavior를 시험한 뒤 제한적으로 적용해야 함.

- 1단계: package ecosystem·manifest·lockfile·SBOM·private registry·runner inventory와 alert enablement 대조
- 2단계: synthetic malicious/withdrawn advisory로 alert delivery·dependency matching·ticket escalation·suppression expiry 검증
- 3단계: confirmed package에서 block·cache purge·rebuild·artifact provenance·credential rotation·post-incident review drill

#### 개발팀/인프라팀 체크리스트

malware advisory가 올라온 순간부터 package version을 지우는 순간까지 dependency graph와 execution evidence가 끊기지 않아야 함.

- 체크: npm·PyPI·Maven·RubyGems·NuGet·Go·crates.io·Composer별 manifest/lockfile/SBOM coverage 확인
- 체크: Dependabot malware-alert opt-in, notification routing, alert API/export, withdrawal 재평가 SLA 확인
- 체크: self-hosted runner·cache·private registry·signing/deploy credential·artifact retention을 incident runbook에 포함

#### 강조 메세지

새 alert coverage의 가치는 number of alerts가 아니라 악성 package가 실제 build 또는 endpoint에서 실행되기 전에 dependency path를 닫고, 이미 실행된 경우 credential과 artifact trust를 회복하는 시간에 있음.

- 강조: advisory feed의 사실과 organization exposure의 사실을 혼동하지 않을 것
- 강조: auto-publish의 속도와 withdrawal/false-positive 대응을 같은 운영 계약으로 설계
- 팀 액션: 다음 supply-chain tabletop에서 alert·lockfile·runner log·token rotation·artifact rebuild evidence를 끝까지 연결
