### Cloudflare Q3 DDoS: short-burst·DNS/UDP 전환에 맞춘 edge-to-origin 방어 검증

한 줄 결론: Cloudflare는 2026년 3분기 network-layer DDoS 1,820만 건과 HTTP DDoS 요청 14.4조 건을 자동 완화했다고 집계함. 10분 미만·1Gbps 미만 공격이 전년 동기 대비 208% 늘어, 최대 대역폭 수치보다 짧은 burst에서 edge·L4·origin이 실제로 차단·복구되는지 같은 시간축에서 검증해야 함.

- 일일 재검토: 2026-10-30 06:55 KST

#### 한 줄 결론

Q3 관측에서 두드러진 변화는 대형 단발 공격의 절대 건수보다 짧고 반복적인 burst의 증가임. 방어 설계는 최고 Gbps를 견디는지뿐 아니라 10분 이내 UDP·DNS burst가 edge에서 origin까지 도달하기 전에 자동으로 식별·제한되고, 사용자 오류와 connection saturation이 정상화되는지를 검증해야 함.

- 변화: 10분 미만·1Gbps 미만 공격이 전년 동기 대비 `208%` 증가한 관측
- 결정: 최대 대역폭 중심 capacity test에 detection-to-mitigation latency·connection error·origin bypass 검증 추가

#### 원문과 관련 뉴스의 핵심 내용

Cloudflare는 2026년 7~9월 자사 네트워크에서 자동 완화한 DDoS telemetry를 공개함. 이 수치는 Cloudflare 보호 traffic의 관측치이며 인터넷 전체나 개별 조직의 위협 빈도를 직접 대표하지 않음.

- 집계: network-layer DDoS `1,820만 건`, HTTP DDoS 요청 `14.4조 건`, network-layer 시간당 약 `8,226건`
- 규모: network-layer 272.6PB, HTTP layer 95.1PB 완화 traffic 범위
- 대조: 1Tbps 초과 공격은 Q2 `805건`에서 Q3 `251건`으로 감소했으나 위험 감소 일반화 불가

#### 공격 벡터와 관측 경계

CLDAP 반사·증폭 비중은 크게 줄었지만 connectionless protocol 위험이 사라진 것이 아니라 DNS amplification과 일반 UDP flood 쪽으로 구성 비중이 이동한 것으로 집계됨. 특정 벡터가 줄었다는 사실은 open resolver, 노출 UDP service, spoofed traffic path가 안전하다는 증거가 아님.

- 변화: CLDAP 비중 `99.5%` 감소 후 network-layer attack의 `0.05%` 범위
- 변화: DNS amplification `215%` 증가해 `3.43%`, 일반 UDP flood `14.06%→31.31%` 확대
- 경계: provider telemetry와 고객 origin·transit·on-premise packet visibility의 coverage 차이 확인 필요

#### AI/Infra 전문가 해석

short-burst 공격은 사람이 ticket을 열고 판단하기 전에 끝나거나 재시작될 수 있음. 따라서 control plane은 burst 자체를 탐지하는 rule, data plane은 drop·rate limit·scrubbing 경로, application plane은 connection·CPU·egress·error budget 영향을 각각 남기되 공통 incident ID로 묶어야 함.

- 볼 것: edge mitigation event와 L4/L7 error·connection count·autoscaling event의 timestamp 정렬
- 피할 것: CDN dashboard의 mitigated 수치만으로 origin saturation 또는 사용자 영향 부재를 결론내는 운영

#### 아키텍처·운영 관점

방어 경로는 public ingress, CDN/WAF, L4 load balancer, stateful firewall/NAT, origin subnet, upstream transit의 순서로 inventory화해야 함. direct-origin CIDR이나 관리 endpoint가 남아 있으면 edge rule이 정상 작동해도 우회 traffic이 back-end state를 소진할 수 있음.

- 설계: origin inbound를 known proxy·load balancer source로 제한하고 public UDP listener와 resolver를 service owner별로 등록
- 운영: 10분 미만 burst에 대해 edge decision·drop counter·NAT/state table·connection pool·p95/p99 error를 동일 dashboard로 조회

#### 비용·신뢰성 관점

방어 비용은 scrubbing 계약이나 egress 단가만이 아니라 로그 보존, false positive investigation, upstream escalation, autoscaling, incident recovery를 포함함. 낮은 대역폭도 요청·connection rate가 높으면 service degradation을 만들 수 있어 Mbps와 PPS/CPS, state exhaustion, detection delay를 함께 측정해야 함.

- 측정: detection-to-mitigation latency, PPS/CPS, dropped/served ratio, connection error, recovery time, false positive
- 결정: DDoS drill의 pass 기준을 평균 throughput이 아닌 customer-facing error budget과 origin resource saturation으로 설정

#### 보안·거버넌스 관점

DNS recursion, UDP service, open resolver, direct-origin address는 공격 표적이면서 reflection source가 될 수 있음. 운영 책임자는 public exposure와 방어 provider configuration을 분리하지 말고 change record·asset owner·exception expiry·upstream contact를 함께 관리해야 함.

- 통제: public DNS resolver·UDP listener·origin CIDR·management endpoint의 exposure inventory를 정기 대조
- 통제: emergency rate-limit 또는 ACL 변경의 승인·rollback·customer impact evidence를 runbook에 기록

#### 개발팀/인프라팀 체크리스트

SRE와 network 팀은 synthetic burst 또는 안전한 test traffic으로 탐지부터 정상화까지의 경로를 재현해야 함. application 팀은 rate limit이 legitimate client, webhook, DNS dependency에 주는 false positive도 함께 측정해야 함.

- 체크: 10분 미만 UDP/DNS scenario에서 edge·WAF·L4·firewall·origin alert 시간이 순서대로 남는지 확인
- 체크: direct-origin 접근, public resolver, UDP listener, upstream scrubbing escalation 번호가 최신인지 확인
- 체크: mitigated event와 p95/p99 latency·5xx·connection saturation·autoscaling을 단일 timeline에서 조사 가능한지 확인

#### 강조 메세지

Cloudflare 보고서의 실무 메시지는 공격의 평균 크기가 작아졌다는 안도가 아니라, short-burst 방어가 사람보다 자동 control plane의 품질에 의존한다는 점임. 이번 주에는 대역폭 benchmark를 다시 수행하기보다 가장 취약한 public endpoint 하나로 detection·mitigation·origin isolation·forensic log retrieval drill을 실행할 필요.

- 발표 포인트: `1,820만 건`·`14.4조 요청`·short-burst `208%` 증가·DNS/UDP vector 전환
- 즉시 행동: service 한 개의 10분 미만 burst runbook에서 edge event부터 origin recovery까지 실제 timestamp를 수집

### Amazon Bedrock AgentCore CLI v1.0: terminal control plane을 agent 운영 증거로 닫는 방법

한 줄 결론: AWS는 `@aws/agentcore` 1.0.0을 GA로 공개하고 project 없이 harness·runtime·memory·identity·gateway·payments resource를 terminal에서 직접 다루는 경로를 제공함. CLI의 편의성은 workstation·CI·agent tool의 cloud write surface를 넓히므로, command·identity·target ARN/Region·결과·rollback을 하나의 deployment evidence로 연결해야 함.

- 일일 재검토: 2026-10-30 06:55 KST

#### 한 줄 결론

AgentCore CLI v1.0의 운영상 변화는 agent resource를 terminal에서 직접 다룰 수 있다는 점임. 생산성 판단은 command 수나 shell 편의성이 아니라 누가 어떤 credential로 어느 Region의 어떤 ARN에 변경을 적용했고, 결과와 rollback을 재현할 수 있는지로 내려야 함.

- 변화: project workflow 없이 supporting resource direct control 경로 제공
- 결정: CLI command를 deployment artifact와 같은 change evidence로 취급

#### 원문과 관련 뉴스의 핵심 내용

AWS는 `@aws/agentcore` 1.0.0 general availability를 공지함. terminal에서 agent와 지원 resource를 create·develop·deploy·operate하는 CLI이며 faster startup, consistent command structure, broader resource support가 공식 범위임.

- 공식 범위: harness·runtime·memory·identity·gateway·payments resource 직접 제어
- 공식 범위: existing resource ID 또는 ARN invoke, interactive shell, harness export, searchable menu·resource picker·guided workflow
- 공식 범위: common global flag의 Region·JSON output·debug·version 적용과 `agentcore migrate` 제공

#### AI/Infra 전문가 해석

agent framework CLI는 단순 local developer tool이 아니라 identity broker와 resource control plane 사이의 translation layer가 될 수 있음. 같은 command라도 local profile, federated role, CI OIDC session, agent-run credential에 따라 권한·network path·audit principal이 달라져 automation 안전성은 CLI 문법보다 execution context에서 결정됨.

- 볼 것: command invocation·effective principal·target account/Region·ARN·request ID·result artifact의 연결
- 피할 것: GA 표기를 IAM least privilege, resource availability, migration correctness의 자동 증거로 해석

#### 아키텍처·운영 관점

개발자 terminal·CI runner·self-hosted agent는 서로 다른 trust zone으로 모델링해야 함. discovery, plan, deploy, invoke, migrate, interactive shell은 write 영향도와 recovery 방식이 다르므로 동일 role 또는 장기 access key로 묶지 않아야 함.

- 설계: read-only discovery role과 scoped deployment role을 분리하고 target account·Region·resource type을 condition으로 제한
- 운영: JSON output과 command log를 secret redaction 뒤 immutable build/deploy record에 연결
- 운영: interactive shell command는 session identity·start/end·target resource·approval ticket을 별도 audit event로 보존

#### 보안·거버넌스 관점

terminal과 agent tool은 shell history, environment variable, debug output, copied ARN, cached credential을 통해 민감 정보를 남길 수 있음. command argument가 external input 또는 agent planning 결과에서 유래할 수 있으므로 untrusted instruction을 privileged action으로 바로 변환하지 않는 policy gate가 필요함.

- 통제: short-lived federated credential·MFA 또는 workload identity를 사용하고 shared profile·long-lived secret을 제거
- 통제: destructive/write command에 account/Region allowlist, human approval, change window, rate limit과 break-glass audit 적용

#### migration·rollback 관점

`agentcore migrate`는 기존 project의 v1 전환 경로를 제공하지만, 생성된 configuration과 resource mapping이 환경마다 동일한 runtime behavior를 보장하지는 않음. migration은 sandbox에서 diff를 검토하고 canary를 거쳐 기존 configuration, artifact version, credential policy로 되돌릴 수 있어야 함.

- 검증: migrate 전후 resource ID·ARN·Region·IAM action·runtime configuration diff를 machine-readable로 저장
- 검증: failed migration·partial resource creation·permission denial·Region mismatch에서 cleanup과 rollback이 재현되는지 확인

#### 비용·신뢰성 관점

agent resource의 운영 비용은 CLI package 자체가 아니라 runtime invocation, memory, gateway traffic, observability, failed retry, human review에서 발생함. direct resource control은 orphan resource와 unintended invocation을 만들 수 있으므로 tag, budget, TTL, concurrency, cleanup을 command workflow에 포함해야 함.

- 측정: command success/failure, retry, orphan resource count, invocation cost, interactive session duration, rollback time
- 결정: deploy/migrate 권한은 cost budget·environment capacity·error budget breach signal과 함께 제한

#### 도입 로드맵

첫 단계에서는 read-only inventory와 sandbox resource invoke로 command audit 및 identity boundary를 검증하고, 이후 low-risk development environment에서 deploy와 migrate를 canary로 확대해야 함. production write는 target allowlist, mandatory CI, approver, rollback evidence가 반복적으로 확인된 뒤에만 부여할 범위.

- 1단계: package provenance·version pin·OIDC/federation·read-only discovery trace 확인
- 2단계: non-production에서 scoped deploy와 `agentcore migrate` diff·cleanup·rollback 검증
- 3단계: production은 protected environment·approval·short-lived session·post-deploy evidence 조건으로 제한

#### 개발팀/인프라팀 체크리스트

개발팀은 command contract와 expected JSON result를, platform 팀은 identity·network·runner isolation을, security 팀은 command audit·secret redaction을, SRE는 failure handling·cost guardrail을 소유해야 함. agent가 CLI를 호출한 경우에도 사람 command와 같은 evidence retrieval 경로가 필요함.

- 체크: package integrity·version pin·allowed registry와 local/CI installation path가 기록되는지 확인
- 체크: every write command에 effective principal·account·Region·ARN·request ID·result·approval이 연결되는지 확인
- 체크: timeout·partial failure·wrong Region·wrong ARN·credential revoke 후 cleanup/rollback drill이 통과하는지 확인

#### 강조 메세지

AgentCore CLI v1.0 도입의 첫 작업은 새 command를 production에 연결하는 일이 아니라, 현재 사용 중인 한 command의 identity와 target을 바꿔도 guardrail이 차단하는지 검증하는 일임. terminal control plane은 빠른 실행 경로이면서 동시에 production change path임.

- 발표 포인트: `@aws/agentcore` 1.0.0 GA·direct resource control·interactive shell·`agentcore migrate`
- 즉시 행동: non-production에서 deploy command 한 건의 profile/role·Region·ARN·JSON result·CloudTrail/CI evidence·rollback을 change ID로 묶어 확인

### 1. Cloudflare DDoS 위협 보고서: 짧은 저대역 공격 급증, DNS amplification·UDP flood 비중 확대

- 발행: 2026-10-29 21:55 KST
- 분류: Security | 태그: Cloudflare, DDoS, Threat Intelligence, Network Security, DNS, UDP, Botnet
- 출처: [Cloudflare Blog](https://blog.cloudflare.com/ddos-threat-report-2026-q3/)

핵심: Cloudflare는 2026년 3분기에 network-layer DDoS 1,820만 건과 HTTP DDoS 요청 14.4조 건을 자동 완화했다고 집계함. 10분 미만·1Gbps 미만 공격이 전년 동기 대비 208% 늘고, CLDAP은 감소한 반면 DNS amplification과 일반 UDP flood가 늘어 대형 단발 공격보다 짧고 반복적인 방어·관측 경로의 중요도가 커진 범위임.

Cloudflare의 네트워크 telemetry 기반 Q3 보고서는 시간당 약 8,226건의 network-layer DDoS 완화와 공격 벡터 변화를 제시함. 1Tbps 초과 공격은 전 분기 805건에서 251건으로 줄었으나, 이 수치를 전체 인터넷 또는 개별 서비스의 위험 감소로 해석할 수는 없음. 조직은 edge·upstream·origin의 UDP/DNS rate limit, autoscaling·alert threshold, 짧은 burst의 로그 보존·사후 분석 가능성을 실제 트래픽으로 점검해야 함.

#### 무슨 일이 있었나

Cloudflare Cloudforce One은 2026년 7~9월 자사 네트워크에서 관측·완화한 DDoS 추세를 공개함. 이 데이터는 Cloudflare 보호 트래픽의 telemetry이며 모든 인터넷 또는 특정 산업 전체의 표본을 뜻하지 않음.

- 집계: network-layer DDoS `1,820만 건`, HTTP DDoS 요청 `14.4조 건`을 Q3에 자동 완화한 수치
- 빈도: network-layer 기준 시간당 약 `8,226건`, 하루 약 `197,400건`, 약 0.44초당 한 건의 완화 빈도

#### 본문 핵심 포인트

공격의 중심이 대형 단발 트래픽만이 아니라 짧고 반복적인 burst로 이동한 것으로 보고됨. 짧은 공격은 사람의 수동 triage보다 자동 탐지·완화와 즉시 확인 가능한 telemetry에 더 크게 의존하는 운영 조건임.

- 변화: 10분 미만·1Gbps 미만 attack이 전년 동기 대비 `208%` 증가, 각각 전체의 96%·98% 비중
- 대조: 1Tbps 초과 hyper-volumetric attack은 Q2 `805건`에서 Q3 `251건`으로 감소한 관측
- 지속 위험: Mirai 분류 완화 트래픽이 network-layer bytes의 46.5%를 차지했고, 최장 지속 공격은 49.7시간 범위

#### 공격 벡터 변화

CLDAP 반사·증폭은 Q3에서 급감했지만, 다른 connectionless protocol로 전환된 것으로 집계됨. 특정 벡터 하나의 감소를 UDP reflection risk 또는 open resolver·노출 서비스의 안전 보장으로 확대할 수 없음.

- 변화: CLDAP attack 비중이 전 분기 대비 99.5% 감소해 Q3 network-layer attack의 0.05% 범위
- 변화: DNS amplification은 215% 증가해 network-layer attack의 3.43%, 일반 UDP flood는 14.06%에서 31.31%로 확대

- 사용 사례: small-model inference·AV/ADAS simulation·embedding generation·multi-model serving

#### 본문 핵심 포인트

- 배치: application code 변경 없이 task별 GPU memory·선택적 compute share 기반 배치
- 복구: Managed Instances에서 MPS daemon 비정상 시 instance 교체와 task의 healthy capacity 이동 수행

#### 왜 중요한가
